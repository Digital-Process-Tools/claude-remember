`hooks.d/after_save/60-git-reconcile.sh:448`: `git rebase --abort ... || true`
ignores the abort's own exit status. Exercised by the auditor against a real
scratch store, mode `lockabort` (an `index.lock` present at abort time, as
during a concurrent `git add` by another slug): rebase-merge state was still
present afterward, while the hook's own notice reported "The rebase was
aborted (aborted, the tree is unchanged)". This is the stuck-rebase failure
mode the #939 commit message itself calls worse than the original bug,
because the next `50-git-backup.sh` commit for this slug would commit this
slug's own unresolved conflict markers verbatim.

What would settle it: check the abort's own exit status and a post-abort
`_grc_rebase_in_progress`-style check, then retry or report rather than
assuming success.

Routing: if still open after a further round, route through the ordinary
filing path per findings.md rather than staying a fragment.
