While chasing a CI-reported fork-count flake caused by my own watchdog redesign in
scripts/lib-lock.sh (#1101/#1103 follow-up), I found that
tests/test_lock_timing.py::test_with_the_recorder_off_nothing_is_written_and_nothing_extra_is_spawned
is ALSO flaky against the completely unmodified, pre-lane version of scripts/lib-lock.sh
(origin/fix/1101-1103 before any of this lane's commits) -- 1 failure in 15 runs (~7%),
confirmed by temporarily swapping in that exact pre-lane file content, running the test
repeatedly, and restoring my own working-tree edit afterward, verified byte-for-byte restored.

I had initially assumed I introduced this flake: my OWN watchdog subshell polls with a
`while kill -0 ...; do sleep; done` loop whose very first iteration's outcome depends on
which of two processes (the watchdog itself, or the main thread's own `wait`) gets scheduled
first -- a genuine source of non-determinism I introduced, confirmed by reproducing a 2/15
and later 4/20 failure rate against my own committed code for the exact same test. I
restructured the loop to always sleep once unconditionally before the first check (removing
that specific race), which is a real, independently-justified improvement (deterministic
fork count on the fast path) -- but it did NOT bring the flake rate to zero, because the
test was already flaky before my change for a DIFFERENT, uninvestigated reason.

What I did not determine: the actual root cause of the baseline ~7% flake in that test.
Plausible candidates I did not chase further (time-boxed): the timing recorder's own
clock-resolution probing forking a variable number of times depending on bash feature
detection timing; the test's harness script's two lock_acquire/lock_release round trips
(one fast, one after a 2.5s hold) interacting with the shim-resolution helper's own forking
in a way that is itself timing-sensitive; or generic OS scheduler jitter affecting ANY
fork-count comparison test run back-to-back under load (this session had several other
agents/watchers running concurrently throughout, per a process listing).

Curator: this reads to me as a real, if narrow (~7%), pre-existing flake in this test,
independent of the #1101/#1103 lane's own changes, worth either (a) filing as its own issue
on the tracker (repro: run the single test in a loop via pytest -q --no-cov, ~1-in-14 runs
red) with the finding above pasted in, or (b) deciding it is below the bar for action given
the rate and not something this lane should hold up a PR to chase. I did not file it myself
since filing is outside this phase's job and I was not confident enough in which of the
plausible causes above is the real one to write a reliable repro-with-mechanism bug report
rather than just a repro.
