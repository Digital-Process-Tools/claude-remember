Gate-3 release audit finding (round 1, v0.45.0..HEAD, dispatch token bcdfab0ecd6fbe1a)
against the v0.45.0 release (#1115), logged as a trap.d/ fragment per the non-blocking
routing rule in skills/manager/phases/findings.md -- ranking-table row `fails-to-preserve`,
"can ship behind a trap.d fragment".

## What

`_lock_read_pid_timeout` in scripts/lib-lock.sh (lines 233-401) only reports a failure when
`wait` returns 128 or more -- i.e. the watchdog killed the read because it hung. If the
underlying `cat` instead fails FAST with an ordinary non-hang error (exit 1: EACCES, EIO, a
cloud-storage placeholder that errors rather than hangs), the helper returns 0 with an empty
result, and `_lock_try_steal` (lines 527-528) treats that empty value as "confirmed empty --
the read genuinely completed", the same as a lock file that is legitimately empty. The only
remaining gate is the 30s `_LOCK_ADOPT_AFTER` age check; the re-read at 566-574 fails the same
way, so empty matches empty and the noclobber write at 585 steals the lock.

This is a regression from e704ea2 (#1101/#1103): at v0.45.0 an empty pid was never stolen
(`[ -n "$_pid" ] ... || return 1`).

## Impact

A second process can take save.lock / consolidation.lock / staging.lock away from a holder
that is still alive and has simply held the lock past 30s, whenever the pid-file read fails
fast rather than hanging. Two critical sections then run concurrently -- the duplicate-save
class (#142/#168) the lock exists to prevent, including two concurrent `run-consolidation.sh`
invocations both appending to the same destination file (run-consolidation.sh:256).

## How it was confirmed

Small bash harness in the session scratchpad (not the suite, deleted after use): a live
`sleep 300` holder, lock dir mtime set 60s in the past, then `lock_acquire "$L" 0` run against
HEAD and against `git show v0.45.0:scripts/lib-lock.sh`.

```
== HEAD
readable: refused
unreadable: ACQUIRED while holder alive=yes
== v0.45.0
readable: refused
unreadable: refused
```

The readable case is the positive control (the harness does not always acquire); the
unreadable case (chmod 000, a fast non-signal failure) splits HEAD from v0.45.0.

## Test gap (reasoned)

`tests/test_lock_primitive.py::test_an_unreadable_pid_file_is_refused_quickly_rather_than_hanging`
(line 547) uses a FIFO, so it only models a read that HANGS, never one that fails fast.
`changelog.d/1101.fixed.lock-staleness.md` claims an empty pid is reclaimed "exactly as it
already was" -- not true for a pid file that exists but is empty due to a fast read failure;
v0.45.0 never stole one.

## What would settle whether this blocks a future release (`destroys` vs `fails-to-preserve`)

Does any path guarded by save.lock, consolidation.lock or staging.lock rewrite a memory file
IN PLACE rather than append/stage? If one does, two concurrent holders can lose data with no
copy left, and the row becomes `destroys` rather than `fails-to-preserve`.

## Fix direction

`_lock_read_pid_timeout` should return a distinct "read failed" state for a non-zero exit
below 128, and callers (`_lock_try_steal` and the adopt re-read) should treat that state like
a timeout -- i.e. refuse to steal/adopt -- rather than like a confirmed-empty file.
