Found by the release-auditor during the v0.42.0 release gate 3 audit (round 3,
range v0.41.0..HEAD), ranked `fails-to-preserve` (non-blocking) per
skills/manager/phases/findings.md. Logged as a trap.d fragment per that
table's "can ship behind a trap.d fragment" row. **This is a regression
introduced by commit 84a6ea5 (#945)**, the same commit this round's gate
audits. Related to #939, #942, #943, #946.

`hooks.d/after_save/60-git-reconcile.sh:467`: `git symbolic-ref HEAD
refs/heads/$BRANCH_NAME` restores HEAD to the CONFIGURED branch, not to
whatever branch the rebase actually started from (which git itself records
in rebase-merge/head-name, and which can differ from the configured branch).

Reproduced by the auditor against real scratch stores:
- working on branch `work` with `main` configured: HEAD was silently switched
  to `main` (which was behind `work`), `$SLUG` was reset to main's content
  instead of work's, and work's own other-slug content was left staged on
  top of main;
- a configured branch with no local ref at all (e.g. `backup`): HEAD ends up
  pointing at an unborn `refs/heads/backup`, `$SLUG` keeps its conflict
  markers, and every file in the tree reads as freshly added (`A`).

What would settle it: read the rebase's own recorded head-name (from
rebase-merge/head-name, available before `rebase --quit` discards it) and
restore HEAD to that branch, rather than to the configured `$BRANCH_NAME`;
or refuse when the two differ instead of silently switching branches.

Routing: if still open after a further audit, route through the ordinary
filing path per findings.md rather than staying a fragment.
