Found by the v0.42.1 release's gate 3 audit (round 3, the post-kill-switch re-audit, range v0.42.0..HEAD),
rank `misreports`, non-blocking.

`hooks.d/after_save/60-git-reconcile.sh:102` writes a line to `logs/hook-errors.log` on *every*
successful save for *every* installed user, including those with the default `git_reconcile.enabled:
false`. Confirmed by a control with `enabled:false`: rc 0, and `hook-errors.log` still gets
`[git-reconcile] disabled pending #969 ...` appended.

Effect: `/remember:doctor` (`scripts/doctor.sh:957-961`) reports `WARN hook-errors.log is non-empty`
permanently; its `tail -n 5` fills with this line within about 5 saves, so a real error scrolls out and
the "Recent errors" check is effectively disabled; `rotate_logs` only ages `memory-*.log`, so this file
grows one line per save with no limit. It also breaks the contract in
`tests/test_haiku_failure_reaches_hook_errors_694.py:69-82` ("an ordinary successful save must not write
anything to hook-errors.log") -- invisible to that test because its stub plugin ships no `hooks.d/`.

Possible fix (not applied here): read `git_reconcile.enabled` only to decide whether to print the
notice, while keeping the `exit 0` itself unconditional -- that preserves the kill switch's own
unconditional guarantee while stopping the notice from reaching users who never opted in.
