Self-review audit (round 2) on #974's fix found a third sibling log message in
`hooks.d/after_save/50-git-backup.sh` that still lacks the rotate-credential advice
the other two untrack branches now carry.

The untrack block (lines 622-631) has three branches, all reached only after
`git ls-files` already shows a legacy `$SLUG/config.json` tracked -- i.e. any
`haiku.oauth_token` it carried is already in this store's git history, regardless
of which branch fires:

- line 624, "deferred" (store has other staged changes) -- fixed in 0d2b8d3, now
  carries rotate advice.
- line 627, "succeeded" (untrack commit landed) -- fixed in 21caa42, carries
  rotate advice.
- line 630, "could not untrack" (`git rm --cached` or `_gb_commit_untrack` failed)
  -- `log "git-backup" "could not untrack $SLUG/logs, $SLUG/tmp or $SLUG/config.json;
  the index was restored and the next backup retries."` -- still has NO rotate
  advice.

A user who hits this third branch (constructible the same way
`tests/test_git_backup_silent_exclude_mkdir_759.py` constructs an ENOTDIR failure,
or any other `git rm --cached` failure) learns nothing about needing to rotate the
credential, and cannot tell "credential never existed" from "credential exists but
this message happens not to say so."

Ranked by the auditor as `misreports`, can ship behind a trap.d fragment, not
blocking -- not fixed in #974 itself to avoid an unbounded sweep of self-review
rounds over an ever-growing set of sibling branches. Candidate fix: add the same
"if that config.json ever carried a haiku.oauth_token... rotate it
(claude setup-token)" sentence to line 630's message, with a red/green test
constructing the `git rm --cached`/`_gb_commit_untrack` failure path (see
test_git_backup_silent_exclude_mkdir_759.py for the ENOTDIR-failure construction
pattern).
