Observed on windows-latest (run 37334787210, all four pytest legs, 30 of 33 failures):
tests/test_case_rewrite_equivalence_898.py fed its inputs as `bash -c SCRIPT runner *inputs`
and got back exactly 25 more rows than inputs -- 25 being the count of non-dot entries in the
repo root. Git Bash rebuilds argv from the Windows command line itself (msys/cygwin
build_argv + globify): an argument Python's list2cmdline leaves unquoted (no space in it) is
glob-expanded against the cwd, so `*` became 25 filenames; its backslashes are glob escapes;
a newline in it is a separator, so "a\nb" arrives as two arguments. ubuntu and macOS were green.

Cost: one full CI round on the PR, four Windows legs. Confirmed only by the arithmetic
(+25 == root entries, +50 for a shape with two glob inputs); the mechanism is read from the
cygwin runtime's behaviour, not reproduced -- no Windows host here.

Fix: tests/_bash_runner.py run_bash_file (script from a temp file) + bash_octal (inputs on
stdin, one `\0ooo`-escaped ASCII line each, rebuilt with `printf -v x '%b'`), and the harness
asserts every row echoes back its input exactly, so a transport that changes an input fails
loudly instead of comparing something else. Side trap found on the way: bash 3.2's
`printf -v x '%b' ""` UNSETS x (5.x assigns ""), so the empty input needs skipping.

Probably wants to be a rule for any test that hands bash adversarial strings through argv on
Windows; there may be older tests with the same shape that only pass because their inputs
happen to be glob-free.
