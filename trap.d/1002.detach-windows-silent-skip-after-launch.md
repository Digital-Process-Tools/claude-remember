Release audit for v0.42.3 (round 1, gate 3) flagged scripts/lib-detach.sh:123-125
(`_remember_detach_windows`), wired from scripts/post-tool-hook.sh:1063-1067.

What was observed: the function backgrounds `wscript.exe //B ... >/dev/null 2>&1 &`
and then unconditionally `return 0`s. The nohup fallback only covers failures
*before* launch (wscript.exe, cygpath or the launcher assets missing). Any failure
*after* wscript starts is invisible to the caller and the save is skipped with no
fallback -- including Windows Script Host disabled by policy, VBScript's
deprecation removing it, or a launch that never reaches the save script. The
comment at lib-detach.sh:16-18 promises the opposite ("a Windows launcher that
cannot run for any reason falls straight back ... a flashed console beats a
silently skipped save").

Where: scripts/lib-detach.sh:123-125, called from scripts/post-tool-hook.sh:1063-1067.
Not covered by CI: the windows-latest legs in .github/workflows/tests.yml:33 run a
stub wscript.exe, not the real one, so this path has never been exercised.

What it would cost a user: PostToolUse saves silently stop on an affected Windows
host, with only the "save triggered" seed line in the log and no fallback save
until the unchanged SessionEnd nohup path runs.

How to confirm: on a Windows host with WSH disabled (or VBScript removed), does
`wscript.exe //B windows-hidden-run.vbs ...` exit non-zero, and does any save
still run? Not yet observed, reasoned from the code and the comment's own promise.

Ranked `fails-to-preserve`, non-blocking per the release-3 ranking table -- logged
here rather than filed, for /oss:curate to triage.
