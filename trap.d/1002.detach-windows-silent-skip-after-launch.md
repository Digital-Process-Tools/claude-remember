Release audit for v0.42.3 (round 1, gate 3) flagged scripts/lib-detach.sh:123-125
(`_remember_detach_windows`), wired from scripts/post-tool-hook.sh:1063-1067.

What was observed: the function backgrounds `wscript.exe //B ... >/dev/null 2>&1 &`
and then unconditionally `return 0`s. The nohup fallback only covers failures
*before* launch (wscript.exe, cygpath or the launcher assets missing). Any failure
*after* wscript starts is invisible to the caller and the save is skipped with no
fallback -- including Windows Script Host disabled by policy, VBScript's
deprecation removing it, or a launch that never reaches the save script. The
comment at lib-detach.sh:16-18 promises the opposite ("a Windows launcher that
cannot run for any reason falls straight back ... a flashed console beats a
silently skipped save").

Where: scripts/lib-detach.sh:123-125, called from scripts/post-tool-hook.sh:1063-1067.
Not covered by CI: the windows-latest legs in .github/workflows/tests.yml:33 run a
stub wscript.exe, not the real one, so this path has never been exercised.

What it would cost a user: PostToolUse saves silently stop on an affected Windows
host, with only the "save triggered" seed line in the log and no fallback save
until the unchanged SessionEnd nohup path runs.

How to confirm: on a Windows host with WSH disabled (or VBScript removed), does
`wscript.exe //B windows-hidden-run.vbs ...` exit non-zero, and does any save
still run? Not yet observed, reasoned from the code and the comment's own promise.

Ranked `fails-to-preserve`, non-blocking per the release-3 ranking table -- logged
here rather than filed, for /oss:curate to triage.

Round 2 update (branch fix/1002-real-wscript-evidence, PR #1010):
RESOLVED, with a real complication caught along the way. scripts/lib-detach.sh
no longer backgrounds wscript.exe with a trailing "&" or unconditionally
returns 0 -- it returns wscript.exe's own exit status, waited for via a
plain bash job-plus-watchdog pair (not the external `timeout` binary, which
is not guaranteed on every host; see below), so a post-launch failure (WSH
disabled, as this fragment describes) now reaches the caller and triggers
the existing nohup fallback.

Real CI evidence, OBSERVED on PR #1010's own windows-latest legs (run
38046309588): tests/test_windows_real_wscript_1002.py's own
WSH-disabled-via-registry case passed on 4 separate windows-latest legs
(pytest 3.9, 3.11, 3.12, and hook-tests-compiled), taking ~10.4s each time
-- the save genuinely happened via the nohup fallback once WSH was
disabled for real.

The first attempt at this fix (foreground wscript.exe, no bound at all)
HUNG the CI job for 40+ minutes on exactly this case -- WSH disabled is
not guaranteed to fail wscript.exe silently; it can surface as a blocking
UI prompt that never resolves on a headless runner, which would have
hung the real PostToolUse hook identically. A bounded wait (bash
background job + watchdog, not the external `timeout` binary -- absent
on a bare macos-latest CI image, which is a host this function's own test
suite simulates Windows on even though it never ships the real route)
closes that hole. See commits eff9d6f, 2490b21 and be5091d on PR #1010
for the sequence.

Round 3 update (branch fix/1002-real-wscript-evidence, PR #1010, maintainer
instruction): this fragment's own hazard was finally observed against the
SHIPPED v0.42.3 shape itself, not just reasoned about from the diff.
`tests/test_windows_real_wscript_v0_42_3_1002.py::test_v0_42_3_wsh_disabled_silent_skip`
drives the vendored v0.42.3 `_remember_detach_windows` with WSH disabled via
the registry, and OBSERVED on PR #1010's own `windows-latest` CI legs (run
#38049234152, jobs 114204833302/114204833300/114204833325/114204833251/114204833202):
the save never happened within the poll window -- confirming trap B exactly
as this fragment originally reasoned, on a real Windows host, for the first
time. Pinned `xfail(strict=True)` with those job ids as the reason, so the
evidence stays observed rather than erased by a future unrelated green run.

Round 3 also fixed a real stall regression the round-2 watchdog introduced:
with WSH disabled, every `_remember_detach_windows` call on the NEW shape
paid the full watchdog bound before falling back to `nohup`, and since
PostToolUse calls this on every tool call, an affected host stalled every
single save by that amount, forever. `scripts/lib-detach.sh` now caches the
"hidden route unusable" verdict after the first failure (keyed on `$PATH`,
mirroring `scripts/detect-tools.sh`'s own #668 tool-verdict cache), so later
saves on that host skip straight to `nohup`. See docs/windows.md for the
full writeup.
