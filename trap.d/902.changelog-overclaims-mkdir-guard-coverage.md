Round-1 release audit for v0.41.0 (delta v0.40.0..HEAD, #911/#912), found by
oss:release-auditor. Ranked `misreports` -- can ship behind a trap.d fragment, not
blocking.

changelog.d/902.fixed.md's own wording ("refuses to `mkdir -p` a `REMEMBER_DIR`
that is not an absolute path or that carries a newline/carriage return, instead
of building a directory tree under the current working directory from it")
overclaims. On every slow path, scripts/bootstrap-dirs.sh:74-79 runs one line
before log.sh (session-start-hook.sh:224 vs :227, post-tool-hook.sh:367 vs :368)
and does `mkdir -p "$REMEMBER_DIR/tmp" "$REMEMBER_DIR/logs" "$REMEMBER_DIR/logs/
autonomous"` with no safety check at all -- the exact tree the #902 guard claims
to prevent is already built by the time the guard runs. On the fast path,
post-tool-hook.sh:413-415, :549 and :681 also run their own `mkdir -p
"$REMEMBER_DIR/tmp..."` ahead of the guard. Neither the PR's own disclosure
(tests/test_remember_dir_guard_902.py:39-55, commit body) nor the shipped
changelog fragment names bootstrap-dirs.sh, the site sitting directly in front of
the guard. The fix that removes the defect: apply the unsafe-dir check at
resolution time (lib-memory-dir.sh `_resolve_remember_dir`) or inside
bootstrap-dirs.sh itself, rather than only at the sites #902 touched; narrowing
the changelog wording is the lesser alternative. Reasoned from reading the code
(release tree + check_release_tree.py run clean against HEAD); the stray-mkdir
route itself predates this delta (present since v0.40.0) and its target is the
user's own `data_dir` config, not an argument slot -- so this is `misreports`
rather than `containment (write)`.
