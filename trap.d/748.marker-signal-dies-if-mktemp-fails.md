#748's audit round (oss:auditor, self-review) found a narrower residual instance of the same
class #748 itself fixed, in scripts/lib-memory-dir.sh's no-jq Python-fallback branch.

The fallback's own drop-disclosure is a marker file, because the interpreter's stdout/stderr are
already redirected to /dev/null by the caller and cannot carry a signal on their own:

    _project_drop_marker=$(mktemp "${SYS_TMPDIR}/remember-config-drop-marker-XXXXXX" 2>/dev/null) || _project_drop_marker=""

If THIS mktemp call itself fails (a full or read-only $TMPDIR), `_project_drop_marker` is empty.
The Python subprocess then receives an empty `drop_marker_path` argument and its own
`if drop_marker_path: ...` guard skips writing the marker even when the untrusted project layer
ALSO fails to load in that same invocation -- so the drop happens with nothing logged, reproducing
the exact #748 defect (silent fail-closed) in this compound, doubly-rare failure case (tmp
exhaustion AND an unreadable/malformed project config, in the same run).

The code's own comment at that line already states this as a deliberate tradeoff -- "tolerated the
same way every other mktemp-failure path in this file is (fall through, don't crash the merge over
the logging side-channel itself)" -- and every OTHER mktemp call in lib-memory-dir.sh (the sanitize
temp file, the merged-config temp file) accepts the identical silent-fallthrough shape on its own
mktemp failure. The auditor ranked this `fails-to-preserve`, non-blocking, "can ship behind a
trap.d fragment" per the findings table -- hence this file rather than a filed issue.

What would settle it, for whoever curates this: whether a compound failure this rare (both mktemp
AND the project config have to fail in the same call) is worth a SECOND, independent signal --
e.g. checking the Python subprocess's own exit code in addition to the marker file, so a failure
disclosure never depends on a SECOND filesystem operation succeeding -- or whether the existing
"every mktemp failure in this file is tolerated the same way" precedent already covers it and this
is working as designed. Not decided here.
