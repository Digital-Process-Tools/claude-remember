Self-review of #1124 (Explore reviewer, finding 4) found that
`_lock_rename_preserves_identity`'s own throwaway probe files
(`.steal-probe.$pid` / `.steal-probe.$pid.moved`, created in the lock
directory's PARENT so the probe does not reset the directory's own
staleness clock -- see the comment above that function) have no reaping
logic the way the `pid.stealing.*` claim files a few lines above do.

A process killed (SIGKILL, OOM) between creating the probe and this
function's own cleanup leaves the leftover behind permanently. Not a
correctness hazard on its own -- nothing reads it back, and a clean
release's `rm -rf "$_dir"` does not reach it either, since the parent
directory is never removed. It is pure disk litter, same class the
pid.stealing.* sweep exists to prevent for claim files, just not applied
here.

Ranked non-blocking (Low-Medium) because the probe now lives in the
lock directory's PARENT rather than inside it, which may be shared by
several unrelated lock directories -- a correct sweep needs to identify
and remove only entries whose owning pid is dead, without touching a
sibling lock's own files, which is more care than the existing
pid.stealing.* sweep needed (that one only ever sees entries belonging
to its own lock directory).

Left as documented-and-accepted in the code comment (scripts/lib-lock.sh,
just above `_lock_rename_preserves_identity`) rather than solved under
this issue's time budget. Worth a dedicated reap pass if this ever
becomes an actual accumulation problem in practice.
