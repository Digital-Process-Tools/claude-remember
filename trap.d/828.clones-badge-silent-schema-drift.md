#828's clones-badge workflow (.github/workflows/clones-badge.yml, "Merge into
history and write the badge" step) reads GitHub's traffic/clones API response
with `.[1].clones // []`. `gh api` only treats a non-2xx HTTP status as a
failure; if the endpoint ever returns 200 with a body that has no `clones` key
(a schema change, or some other 200 shape), `// []` silently substitutes an
empty array and the workflow still reports success -- it just adds nothing to
history.json that day. A reader of the badge cannot tell "genuinely zero new
clones" from "this workflow could no longer parse the API's response";  the
badge would simply plateau with no error anywhere.

Not fixed in #828's own PR: the oss:auditor review that found it ranked it
`misreports` (the report would be accurate if it warned on an unexpected
shape, but currently reports success either way) and non-blocking/trap.d-
eligible rather than a design change worth widening that PR's diff for.

I did not verify against the live API whether a 200-with-no-`clones`-key
response is actually reachable -- this is reasoned from the script's own
error handling (gh api's own exit-code contract), not observed. If real, the
fix is small: after computing `total=$(jq '[.[].count] | add // 0'
history.json)`, also check whether `.[1] | has("clones")` was false on a
run that actually executed the fetch step, and echo a loud warning (not a
failure -- a nightly cron going red on an API hiccup is its own cost) when it
was.
