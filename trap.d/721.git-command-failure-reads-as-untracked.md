Observed while implementing and reviewing the #720/#721 fix (scripts/session-start-hook.sh's
`_remember_handoff_is_tracked`).

Both the exact-case check (`git ls-files --error-unmatch -- "$_rel"` guarded by `>/dev/null 2>&1`)
and the case-insensitive fallback (`git ls-files -z` piped through process substitution, guarded
by `2>/dev/null` and a loop that simply falls through to `return 1` on no matching line) collapse
"git said not tracked" and "git could not answer at all" into the exact same observable outcome:
the function returns 1 (untracked), and the caller proceeds to deliver the handoff as trusted.

A transient git failure -- a corrupt object, an interrupted process, a repository mid-gc, any
non-zero exit from the git binary for a reason other than "no match" -- is silently read as "safe
to deliver" rather than "could not determine, so refuse or say so". This is the wrong-direction
default for a security check: the permissive branch is reached on both a clean negative and an
error.

The oss:auditor found this on the second review pass and ranked it `misreports`, ship-behind-
trap.d-eligible (non-blocking) rather than requiring an immediate fix, on the basis that: (a) this
exact shape already exists in the pre-existing exact-case check, so this diff duplicates a class
rather than introducing a new one; (b) this repo already has a considered three-state model for
the identical hazard, in a different file -- `scripts/lib-case-divergence.sh`'s
`REMEMBER_CASE_STATUS`: `ok` / `diverged` / `unavailable`, explicitly never folding `unavailable`
into `ok`. The header comment there states outright: "An absence produced by this check must never
read as agreement; that conflation is this repo's recurring defect (#296, #299, and the 0.12.0
entry's 'three states, not two')."

So the general shape is a known, named, recurring class in this codebase, with a working precedent
for how to do it right sitting one file away -- and this PR's own new check does not follow that
precedent. Whether this warrants a dedicated jit-context rule ("a security-relevant tracked/present
check gated on git output must not fold 'command failed' into its permissive branch"), or whether
it should just prompt a dedicated fix in `_remember_handoff_is_tracked` giving it its own
ok/tracked/unavailable states (mirroring lib-case-divergence.sh's own shape, with `unavailable`
routing to "refuse the delivery and say why" rather than "deliver"), is for /oss:curate to decide.
