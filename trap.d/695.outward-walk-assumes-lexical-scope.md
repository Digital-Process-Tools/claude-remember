# The #695 scanner's outward walk assumes lexical scope; bash is dynamic

`tests/test_locale_ranges_695.py`'s `_is_protected` picks the innermost function span
containing a line and then walks outward, crediting an enclosing function's
`local LC_ALL=C` to a function merely **defined** inside it.

bash scoping is dynamic, not lexical. The outer `local` is in effect only for calls made
while the outer frame is live, and a nested definition outlives the call that created it.
So a nested function called from anywhere else runs with the caller's locale, while the
scanner reports its ranges protected.

Found by the v0.33.0 release audit, round 2 (`rel-0330-r2-96ee92d0`), ranked `misreports`
— non-blocking, which is why it is here rather than in an issue.

**No instance exists in this tree today.** The only nested pair is `capture_was_seen`
inside `_remember_deferred_phase` (`scripts/session-start-hook.sh`), called from exactly
one place, inside its definer — and the outer function carries no `local LC_ALL=C` anyway,
so nothing is being wrongly credited.

The docstring at `_is_protected` asserts the outward walk is sound ("the nested body runs
with the outer's `local` still in scope"). That holds only for the call-from-within case,
and the docstring should say so — or the walk should stop at the innermost span and accept
the false positives that follow.

What settles it: whether a nested function in this tree may ever be called from outside
its definer. Today, no.
