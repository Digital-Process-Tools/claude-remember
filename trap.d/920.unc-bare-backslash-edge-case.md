Observed while self-reviewing #920's fix for the REMEMBER_DIR safety guard
(oss:auditor spawn, against commit c15e4f3 / branch fix/920).

What was observed: the UNC-shape regex the fix adds to both
`_remember_dir_is_unsafe` (lib-memory-dir.sh, post-tool-hook.sh) and
`_remember_log_dir_unsafe` (log.sh) --
`[[ "$REMEMBER_DIR" != [\\][\\][^\\]* ]]` -- requires a third character after
the two leading backslashes before it treats the value as a safe UNC path. A
bare double-backslash (two backslashes, nothing after) is therefore still
classified unsafe. Windows itself requires at minimum `\\server\share` to be
a real UNC path, so no realistic project-directory value ever takes the
bare-double-backslash shape. The comments and changelog describing this fix
("accepts a UNC-rooted value") are slightly broader than what the regex
technically delivers for this one degenerate input.

Where: scripts/lib-memory-dir.sh and scripts/post-tool-hook.sh (both copies
of `_remember_dir_is_unsafe`), scripts/log.sh (`_remember_log_dir_unsafe`).
The pattern: `[\\][\\][^\\]*`.

What it cost: nothing reachable -- auditor rated this very low severity,
nothing lost or exposed, no realistic caller hits it. Below the intake bar
per findings.md's table (misreports, "can ship behind a trap.d fragment"),
not fixed in #920's pull request.

How it was confirmed: auditor reasoned it from the regex and Windows's own
UNC-path minimum shape; not independently re-derived by this report-writing
spawn.

Unsure whether it belongs elsewhere or is even worth a rule -- logging it
here per the spine's routing for a below-bar finding, no promotion decision
made.
