Release audit (v0.39.0, round 2, oss:release-auditor, dispatch token
rel39-1791028178-23675-r2) found a composition gap between 6f32952/#870 and
e0cbc3c/#894.

pipeline/haiku.py:1636-1648 (plus a hedged sibling in scripts/doctor.sh:978-987): after an
un-isolated retry fails with an auth marker, #870's warning states as fact: "The CLI's own
saved login has expired; configure the plugin's userConfig recovery token instead." #894
then made the userConfig token get injected into `env` once, at line 1540, before the
first attempt -- both attempts reuse that same `env`.

So when the configured userConfig token is itself the dead credential, the warning blames
"the CLI's own saved login" and tells the user to configure the token they already
configured. The same wrong attribution happens when the failing credential is a
host-supplied CLAUDE_CODE_OAUTH_TOKEN, an `invalid api key` from an ambient
ANTHROPIC_API_KEY, or a #316 Bedrock/proxy `invalid bearer token` -- all reach this branch
through `_AUTH_FAILURE_MARKERS`.

What a caller gets: a confident wrong cause, and a circular next step, in the one log line
meant to point at the fix. `misdirects` does not fit (the printed step does nothing the
caller did not ask for); this is a wrong statement of cause, so `misreports` (non-blocking).

tests/test_haiku_isolation_retry_wording_870.py covers only the no-token, expired-login
case (reasoned, not observed).

What would settle it: whether the warning should branch on which credential was actually
in `env` (injected userConfig, host token, or API key) before naming a cause.
