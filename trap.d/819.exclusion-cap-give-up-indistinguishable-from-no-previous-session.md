#819's fix for previous_transcript()'s quadratic pluginless-SDK retry (scripts/session-start-hook.sh)
added a cap on how many excluded candidates the retry will walk past
(_PREV_TRANSCRIPT_EXCLUDE_CAP, default 20). Past the cap, both previous_transcript() and
_second_newest_jsonl() set newest="" and return/print nothing -- the auditor round of self-review
(oss:auditor) flagged that this is byte-for-byte the same output as "there genuinely is no previous
transcript in the directory at all." Neither function logs anything on the cap-hit path.

Downstream, the caller sets PREV_JSONL=""/PREV_ID="" identically in both cases, which silently
skips two consumers: the recovery force-save (`[ -n "$PREV_ID" ]` gate) and the capture-gap "was
this session captured" warning (#200) that this very hook exists to raise. Concretely: a sessions
directory with more than 20 headless pluginless-SDK transcripts ahead of one real, never-captured
previous session now produces NO warning at all -- indistinguishable from a fresh install with no
history. This is a new failure mode #819 itself introduces: the pre-#819 code had no cap and always
eventually found the real transcript (however slowly), so it never had a silent give-up branch to
begin with.

The issue's own text accepts this tradeoff ("a previous session hidden behind that many headless
runs is not worth finding"), so the CAP itself is not in question -- only that nothing currently
distinguishes "gave up, hit the cap" from "nothing to find" for anyone reading logs or debugging a
missed capture-gap report later. The auditor's suggested direction: add a single `log` line on the
cap-hit branch in each function (this repo already logs liberally for comparable "gave up, here is
why" cases -- see #804/#815's config-layer-drop disclosures) so the two cases are told apart in the
field.

Ranked non-blocking (`misreports`) by the manager's own findings table: it does not block the
release, does not corrupt anything, and is a candidate for a small standalone fix later rather than
a rider on #819's own diff. Not filed as a tracker issue for the same reason -- it is small enough,
and specific enough to this one code path, that curation may want to fold it straight into a
jit-context rule about "a bounded retry's give-up branch needs its own signal" rather than open a
separate ticket, but that decision belongs to /oss:curate, not to this lane.
