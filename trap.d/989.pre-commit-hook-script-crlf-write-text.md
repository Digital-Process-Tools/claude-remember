#989 self-review (oss:auditor round): `tests/test_git_backup_rotate_advice_974.py`'s new
`test_could_not_untrack_also_logs_rotate_advice` forces the hook's "could not untrack" branch by
writing a `pre-commit` git hook script that always exits non-zero:

```python
pre_commit.write_text("#!/bin/sh\nexit 1\n")
pre_commit.chmod(0o755)
```

`Path.write_text` with no `newline=""` argument uses Python's default text-mode newline
translation, which on Windows rewrites every `\n` to `\r\n` on write. A CRLF-terminated shebang
line (`#!/bin/sh\r\n`) can make some shebang parsers read `/bin/sh\r` as the interpreter path and
fail to exec, rather than running and exiting 1 as intended -- the script would silently stop
doing what the test relies on it doing.

**Why this is inert today, and stays logged rather than fixed or filed:** the whole test file
already carries `pytestmark = pytest.mark.skipif(sys.platform == "win32", ...)` for an unrelated
reason (#79, bash hook subprocess + POSIX flock/git semantics), so this file never runs on the one
platform where `write_text`'s CRLF translation would matter. CI's own matrix
(`.github/workflows/tests.yml`, `os: [ubuntu-latest, macos-latest, windows-latest]`) confirms
`windows-latest` is exactly the leg this skip exempts, so nothing in CI today exercises the
CRLF path either way.

**What would make this live:** if the #79 skip reason is ever narrowed or removed (e.g. if a
future change makes the bash-hook mechanism itself portable), this specific line needs
`newline="\n"` added, or the content written via `open(path, "wb")` with an explicit `b"...\n"`
payload, before the test could be trusted on Windows. Flag it again at that point rather than
assuming it was caught.
