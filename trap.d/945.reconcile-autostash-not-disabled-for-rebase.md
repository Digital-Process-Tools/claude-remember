Found by the release-auditor during the v0.42.0 release gate 3 audit (round 4,
range v0.41.0..HEAD), ranked `fails-to-preserve` (non-blocking, possible
upgrade -- see below) per skills/manager/phases/findings.md. Logged as a
trap.d fragment per that table's "can ship behind a trap.d fragment" row.
**This is a regression introduced by commit 84a6ea5 (#945).** Related to
#939, #942, #943, #946.

`hooks.d/after_save/60-git-reconcile.sh:533` and `:559` (`git rebase
"$REMOTE_REF"`), combined with the `git rebase --quit` the #943 fix
introduced at `:459`: neither rebase call passes `--no-autostash` (or sets
`rebase.autoStash=false`).

If the user has `rebase.autoStash=true` set (a common git setting) and
another slug has an uncommitted tracked write at the moment a real conflict
happens, git moves that other slug's write into a stash when the rebase
starts. The #943 change to `rebase --quit` (replacing the old `rebase
--abort`) does NOT re-apply an autostash the way `--abort` used to -- the
write is left sitting in `git stash list` instead, with nothing announcing
it. The hook's own notice still claims "aborted, the tree is unchanged",
and `docs/configuration.md` repeats the same "changes nothing else" claim.

Reproduced by the auditor against a real scratch store: another slug's
tracked write reverted to its pre-write content, with the write found only
in `git stash list` (`stash@{0}: autostash`) afterward. Controls: with
autostash off, the write survives (the rebase simply refuses to start
instead). The pre-#945 hooks (both #903's original and #939's fix) kept the
write in both cases -- so this is specifically a regression from #945's
`--quit`-based rewrite, not a pre-existing gap.

Why ranked `fails-to-preserve` rather than `destroys`: a copy exists (the
stash entry), so "no copy anywhere" does not hold today. That copy is lost
on a `git stash drop`/`git stash clear`, or by ordinary git gc once
`gc.reflogExpire` passes (90 days by default) -- if the maintainer counts an
unannounced, silently-expiring stash entry as equivalent to no copy, this
row is `destroys` and blocks a release.

What would settle it: pass `--no-autostash` (or `-c rebase.autoStash=false`)
at both of the hook's own `git rebase` call sites. No existing test covers
autostash behavior (grep for `autostash|autoStash` in the test suite: 0
hits) -- a regression test exercising this exact scenario should accompany
the fix.

Routing: if still open after a further audit, route through the ordinary
filing path per findings.md rather than staying a fragment, and reconsider
the blocking classification per the note above before doing so.
