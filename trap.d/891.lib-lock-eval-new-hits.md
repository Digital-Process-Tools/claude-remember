#891 widened `check_release_tree.py`'s EVAL_OF_SUBSTITUTION pattern (eval
of a command substitution, plus now a bare or embedded variable
expansion) so it finally catches the two exact shapes #864 had to remove
by hand from scripts/log.sh (`eval "_identity=$_identity_raw"`,
`eval "$_assign"`).

A self-review reviewer (Explore, spawned per agents/developer/review.md)
ran the old vs. new pattern over the whole repo and found the widening
also newly flags scripts/lib-lock.sh at lines 595, 596, 668, 669 and 677
-- e.g. `eval "_LOCK_TIMING_T0_${_LOCK_TIMING_KEY}=\$_LOCK_TIMING_NOW"` --
the same "eval of a dynamically-built variable assignment" shape #864 had
to fix in log.sh. scripts/lib-lock.sh is not in
.github/release-branch.json's deny-list, so it ships in the release tree
check_release_tree.py actually scans: the next CI run that builds a
release tree after this PR merges will start emitting 5 new REVIEW-only
(non-blocking) findings nobody in #886/#887/#891 triaged or decided is
expected.

This is almost certainly the check doing its newly-widened job correctly
-- it is the exact risk class #864 was fixing, just in a sibling file --
but it is a real, untested, unfiled behavioral side effect of this PR on
a file the PR never touches. Worth a human decision: either file an
issue to apply the same #864-style treatment to lib-lock.sh (replace its
own eval-of-variable-expansion with the printf -v pattern, or an

and say so somewhere a future triage pass would see it.

Not decided here, logged only -- /oss:curate is the right place to turn
