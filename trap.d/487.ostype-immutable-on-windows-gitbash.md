Tried to force $OSTYPE away from its real value inside a bash process running
under real Windows Git Bash (windows-latest GitHub Actions runner), to exercise a
negative-control test path (a case statement gated on `case "$OSTYPE" in
msys|cygwin)`). Two independent mechanisms were tried, in two separate CI rounds:

1. `subprocess.run([...], env={**os.environ, "OSTYPE": "linux-gnu"})` from Python,
   spawning the real Windows Git Bash binary. Confirmed via CI job log
   (job 100892436094, PR #499): the spawned bash still read $OSTYPE as its own
   real value (observed as "cygwin" elsewhere in the same run), not the forced one
   -- the block under test still normalized a backslash path as though $OSTYPE
   were msys/cygwin, i.e. the override had literally no effect.

2. `local OSTYPE=linux-gnu` inside a wrapping bash function, in the same script
   passed to the same bash binary via `bash -c script`. Verified locally on macOS
   that this mechanism DOES correctly shadow $OSTYPE within a function on ordinary
   bash (`local OSTYPE=fakevalue; echo $OSTYPE` inside a function prints
   "fakevalue"). On the real Windows CI runner (job 100895310415, PR #499):
   IDENTICAL failure to attempt 1 -- the override still had no effect.

Cost: two full CI round-trips (~5 min each plus investigation time) were spent
before concluding the test's own premise (simulate "not Windows Git Bash" while
literally running Windows Git Bash) is not achievable this way on that platform,
and the test was skipped there instead (`@pytest.mark.skipif(sys.platform ==
"win32", ...)`).

Confirmed how: two independent override mechanisms, same negative result, on two
separate real CI runs, is treated as strong reproducible evidence -- not proof.
Nobody inspected the actual bash/MSYS2/cygwin build's own source or config from
this session to find the real mechanism (e.g. whether $OSTYPE is compiled in as a
dynamic/special variable with its own get/set hooks on that particular build, the
way $RANDOM or $SECONDS are on ordinary bash). `readonly -p` on that same bash
shows OSTYPE is NOT marked readonly, which rules out the simplest explanation.

Unsure whether this generalizes to git-bash on windows-latest specifically, to
MSYS2 in general, or to some other detail of that one runner image -- flagging as
possibly a real, reusable rule (any future Windows-conditional bash logic test in
this repo that needs to simulate "the OTHER branch of an OSTYPE-gated case
statement" will hit the identical wall) rather than a one-off. Logged rather than
promoted to a jit-context rule, per the developer brief's own instruction not to
make that curation call mid-lane.
