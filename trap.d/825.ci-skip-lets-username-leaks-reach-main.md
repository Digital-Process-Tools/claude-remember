#825's own root cause: `tests/test_no_real_home_paths_467.py::test_no_tracked_file_leaks_the_current_machine_username`
is the only guard that scans every tracked file for a real leaked username, and it unconditionally
skips itself whenever `CI` or `GITHUB_ACTIONS` is set (by design -- documented at length in that
file's own docstring, arguing that a CI runner's account name, e.g. `runneradmin`, is not evidence
of anything and asserting against it just manufactures false positives one CI image at a time,
per #472/#442).

The side effect: this class of regression -- a real local username/path pasted into a tracked file
-- can merge to main with a fully green CI run and only ever gets caught on a maintainer's own
machine, on demand, if they happen to run the full suite locally before merging. #822's fix (PR
#824) shipped exactly this shape once already: it scrubbed the file the issue named, but
reintroduced the same real username into two *other* files the same commit added, and CI stayed
green throughout. #825 is the second occurrence of the identical shape.

Not fixed as part of #825: a real fix needs a genuinely CI-safe way to assert "no tracked file
contains a *specific stored* human username" without either (a) a per-image skiplist that grows
one entry per new CI account name (the thing #472 already rejected), or (b) some other mechanism
that tells a maintainer's real username apart from a CI runner's account name reliably. That is a
design decision, not a one-line change, and is exactly the kind of thing #825's own text flagged as
"worth considering, not required for this issue." Logging here rather than filing an issue outright,
since it is non-blocking and the curation pass is better positioned to decide whether this becomes
a jit-context rule, a filed issue, or is judged not worth the complexity the fix would add.
