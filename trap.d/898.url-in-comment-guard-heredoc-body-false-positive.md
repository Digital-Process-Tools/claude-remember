`_check_url_in_comment` (new in `.github/scripts/check_release_tree.py`, #898) flags any
line in a shipped text file whose stripped form starts with `#` and contains something that
looks like a URL host. A reviewer caught a latent false-positive this misses: a line inside a
typed `<<EOF ... EOF` heredoc body that happens to start with `#` and mentions a URL-shaped
host would be misclassified as "a URL host in a comment" even though it is heredoc content,
not an actual shell comment -- the function has no heredoc-boundary tracking at all, unlike
`check_release_tree.py`'s own `_in_code()` helper, which already tracks fenced-code state for
a sibling markdown check.

Not fixed in #898: grepped every currently-shipped `scripts/*.sh` and `hooks.d/**/*.sh` for a
`#`-prefixed line with a URL host inside any heredoc body -- zero hits, so this is not live
today. The typed-heredoc guard itself is REVIEW-only (not FAIL) in this same diff, for the
unrelated reason that this repo's real scripts use ~12 ordinary shell heredocs the portal has
not actually been confirmed to hold on -- so the URL-in-comment misclassification this fragment
describes, if it ever fires, would also only ever be a FAIL on a line that is not really a
shell comment, inside a file whose heredocs are themselves only under REVIEW.

Confirmed by reading: no shipped file exercises this path, so there was nothing to red/green
test against; implementing heredoc-boundary tracking for this one guard felt like scope beyond
a single-issue lane (it would need the same fence-tracking shape `_in_code()` already has, just
for `<<DELIM ... DELIM` instead of ``` ``` ```). Worth a rule or at least a note the next time
someone touches this function, not decided here.
