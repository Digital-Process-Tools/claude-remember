Self-review on #933 (fast-path/fallback retention boundary fix) surfaced that
`tests/test_autonomous_log_retention_487.py::TestHousekeepingSweepFallbackAndEdgeCases::test_must_not_fire_fast_path_keeps_a_log_between_n_and_n_plus_one_days`
names itself as exercising the fast path specifically, but nothing in the
test confirms `_remember_auto_ref` was actually built by `mktemp`/`touch -d`
on the runner it executes on -- there is no check of filesystem evidence
or captured output proving the fast path, rather than the fallback, ran.
`mktemp` failing is swallowed silently (`|| _remember_auto_ref=""`,
scripts/save-session.sh, no warning logged), so if it ever failed on some
CI runner, this test would silently re-run as a duplicate of its sibling
fallback test one function below, and a green run would not reveal that
the fast path itself was never exercised there.

This was flagged by the `oss:auditor` spawn during self-review, ranked
`misreports` (non-blocking) against the findings table, and is logged
here rather than filed, per that table's "can ship behind a trap.d
fragment" row.

Not unique to #933's new test: every pre-existing (#914-era) fast-path
test in this file follows the identical convention of relying on the real
environment's `mktemp` succeeding, with no positive check that it did --
so this is a sibling instance of an existing gap, not a regression this
diff introduced. It is flagged now specifically because #933's own commit
message frames this new test as proof the fast path's own boundary was
fixed, which is the exact claim the missing check would undermine if
`mktemp` ever silently failed in CI.

What would settle it: an assertion (or a captured marker written by the
extracted block itself) proving `_remember_auto_ref` was non-empty /
the reference file existed during the specific test run, for every
fast-path test in this file, not just the new one -- worth the curator's
attention as a class rather than a one-off patch to a single test.
