Implementing the shared #754/#755/#756 injection guard, the first draft made
`_remember_may_inject`'s git-tracked check unconditional -- ask git about the
file's own directory, refuse if tracked, no further gate. That is exactly
what the issues asked for read in isolation, and it passed every #721/#747
regression test plus all 10 of the new #754/#755/#756 cases the first time.

It broke `tests/test_delivery_record_per_machine_285.py` (a pre-existing,
unrelated-looking test) in the full suite: `TestDeliveryRecordIsPerMachine
::test_first_delivery_on_second_machine_does_not_read_as_already_seen`
failed with "the handoff must still be delivered" even though nothing about
that test's own fixture looked related to a symlink or a hostile repo.

The cause: external-storage mode's REMEMBER_DIR can be, and in that test's
own fixture genuinely is, a subdirectory of the user's OWN private git
repository -- the git_backup feature (`hooks.d/after_save/50-git-backup.sh`,
#253) commits memory files into it on purpose, to sync a store across
machines. A generic "ask git about the file" check cannot tell that
apart from a hostile cloned project shipping a poisoned `.remember/*.md`
committed into ITS repo -- both are, mechanically, "a file some git
repository tracks". The two cases differ only in WHICH repository: the
project the user cloned (untrusted) vs. the store's own backup repo the
plugin itself writes into (trusted by construction).

The original, pre-existing `_remember_handoff_is_tracked` (#721/#747) had
exactly this distinction built in, as a precondition most readers would
skim past: "True only in legacy mode (REMEMBER_ROOT == MEMORY_PROJECT_DIR)".
That equality is not incidental -- it is the entire thing that kept the
#721 guard from firing on external storage in the first place. Generalizing
"how do I know if this file is tracked" (the #754 ask) without also keeping
"should I even ask" (the original scope) silently widens the blast radius
of a security fix into a feature it was never meant to touch.

Lesson for next time a security fix generalizes an existing narrow check:
grep for what USES the thing being generalized, in the whole suite, not
only in the test file the issue itself names -- `test_delivery_record_per_
machine_285.py` never mentions #721, #747, #754, #755 or #756 anywhere in
its own text, and there was no way to find it from the issue bodies alone.
Only a full-suite run before handing back caught it; the four targeted
test files this task was scoped to would all have stayed green.
