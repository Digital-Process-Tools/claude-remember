#804's self-review (oss:auditor) found a real, pre-existing gap adjacent to the fix, ranked
`misreports`, non-blocking, disposition "ship behind a trap.d fragment."

`scripts/lib-memory-dir.sh`'s no-jq Python-fallback merge (the same heredoc #804 touched) loads
each TRUSTED config source (any `sys.argv[5:]` entry that is not the untrusted-haiku path -- e.g.
a corrupted `~/.remember/config.json` or `${REMEMBER_DIR}/config.json`) with a bare
`with open(path) as f: data = json.load(f)`, no `try/except`, at what is now lines ~750-752. If
that file is malformed JSON, `json.load` raises uncaught, giving the subprocess a nonzero exit
code that is neither `0` (clean) nor `3` (the new #804 signal for "the untrusted layer was
dropped, merge otherwise succeeded"). The shell's own fallback then does
`cp "$_bundled_cfg" "$_merged_cfg"` for any such nonzero code, and #804's own disclosure guard
(`marker file exists OR rc == 3`) is false in this case -- no WARNING at all. A caller sees the
identical silent "fell back to bundled config" behaviour whether nothing but bundled config
existed, or a TRUSTED file the user actually wrote was corrupt and silently discarded.

This is pre-existing (identical shape existed before #804, via the same bare `|| cp ...` on any
nonzero exit) -- not a regression #804 introduced. What #804 changes is the framing: its own
commit message and in-code comments say the fix is "closing the compound 'both fail silently' gap
#748 left open," which reads more broadly than what shipped -- the new signal only covers the
untrusted-haiku-load-failure path, not a general trusted-config parse failure.

What would settle it: whether a malformed TRUSTED config file deserves the same disclosure
treatment as a malformed untrusted one (a third exit code? wrapping the trusted-source
`json.load` in its own try/except with its own marker/rc?), or whether "trusted config is assumed
well-formed, and a parse failure there is an operator error outside this mechanism's scope" is
the intended boundary and just needs saying explicitly in the comment instead. Not decided here.
