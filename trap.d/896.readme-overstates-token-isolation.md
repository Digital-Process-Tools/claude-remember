Release audit (v0.39.0, round 1, oss:release-auditor) found that README.md:175 (added by
#894/#896) says the userConfig recovery token is stored so that "only this plugin's own
save can read it back". That overstates the isolation: `pipeline/haiku.py:_child_env`
(lines 345-356) strips only `CLAUDECODE`, `CLAUDE_JOB_DIR`, `CLAUDE_PROJECT_DIR`,
`CLAUDE_CODE_*` and, conditionally, `ANTHROPIC_API_KEY`. `CLAUDE_PLUGIN_OPTION_OAUTH_TOKEN`
therefore passes into the nested `claude -p` environment on every call, including when the
host already supplies its own token and the recovery token is not injected. On the
un-isolated retry, that nested session runs the user's other hooks.

Ranked `misreports` (non-blocking) against skills/manager/phases/findings.md's table --
`discloses` does not fit (nothing leaves the machine) and `overexposes` does not fit (no
file mode is involved). Marginal exposure is small, because the same processes already
receive `CLAUDE_CODE_OAUTH_TOKEN` through `_CHILD_ENV_KEEP` whenever it is present.

What would settle it: whether to drop `CLAUDE_PLUGIN_OPTION_*` in `_child_env`, or to
reword the README sentence.
