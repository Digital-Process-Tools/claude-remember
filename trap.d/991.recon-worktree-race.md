An `oss:recon` spawn, run with `run_in_background: false` per the developer brief, raced the
lane's own use of the named worktree instead of acting after it.

What happened: the lane's spawn payload named a worktree path
(`<worktree>`) that already existed on disk when the
lane's turn started. The lane used it directly — `git-status`, then `git checkout -b fix/991` —
while concurrently spawning `oss:recon` in the same tool-call batch, pointed at the same path with
the instruction "locate, do not design." The recon agent, running as a background task, itself
ran `git worktree add` against that same path (treating it as not-yet-existing from its own
perspective at dispatch time, or re-deriving it independently), read from it, and then ran
`git worktree remove` on it when done — on the stated reasoning that "the task named that exact
path as the one 'to use' rather than an unnamed dispatcher slot," so it assumed cleanup was its
job.

The result: the lane's own `git checkout -b fix/991` (and the worktree directory itself)
vanished out from under it mid-session, with no error at the time it happened — the next
`cd`/`git-status` call in that same path simply failed with "no such file or directory." The
branch metadata (`refs/heads/fix/991`) survived in the main clone, but the checked-out worktree
directory did not, and recreating it required a second `git worktree add` naming the existing
branch rather than `-b`, since `-b` now failed with "a branch named 'fix/991' already exists."

Cost: one extra round of `git worktree add`/`list` calls to detect and repair, plus this fragment.
Not catastrophic here (no uncommitted edits existed yet when the directory disappeared), but if
edits had already landed before the removal, this would have been a silent loss of actual work —
indistinguishable from a wrong-tree write said to be the dangerous case in
`supertool-cwd-verify-tree.md`'s own jit-context rule, except on the *delete* side rather than the
*write* side.

Confirmed by direct observation in this session: `ls` of the worktree root showed `991` present
before the recon spawn's notification arrived, and absent immediately after it, with the recon
agent's own hand-back message explicitly stating it had run `git worktree add ... ` then
`git worktree remove` against that exact path.

Unsure whether this is a `run_in_background: false` timing nuance (recon's background task
process started before the foreground `cd`/`checkout` calls completed, or ran concurrently with
them despite "do not touch the tree until it returns" being about the *lane*, not about recon's
own internal ordering) or a `oss:recon` design gap (it should never `remove` a worktree it did not
itself create, or never remove one at all when the caller named a path rather than leaving it
unnamed) -- logging as observed, not diagnosed.
