Observed on the v0.31.0 release audit, round 2 (issue #656, following #653 on
PR #655), scripts/save-session.sh and tests/test_marker_write_fifo_653.py.

#653 added `marker_write_ok()` -- refuse a marker path that exists and is not
a regular file, because a `>` on a FIFO with no reader blocks in `open(2)`
before any redirection error exists for `2>/dev/null || true` to catch -- and
wrapped "every marker write site" with it. Two places then claimed
completeness: the helper's own comment ("Every marker write goes through
this") and the static test, whose `_MARKERS` tuple enumerates the four names
the author had in mind:

```python
_MARKERS = ("COOLDOWN_MARKER", "NDC_MARKER", "NOW_DAY_FILE", "NDC_GEN_FILE")
```

A fifth marker, `FAILURE_MARKER` (`tmp/last-summary-failure`), is written at
`save-session.sh:750` unguarded, under `LOCK_DIR`, and its `-f`-guarded read
means a planted FIFO reads as absent, the count becomes 1, and the write hangs
holding the save lock -- exactly the shape #653 fixed for the other four. The
line predates the delta; the delta introduced the claim.

The trap: a static "every site is guarded" check that is fed a hand-kept list
of names is a check that every site *on the list* is guarded. It passes the
moment the list is complete as of the day it was written and says nothing the
day after. The same audit run swept three more of the class outside this file
(`post-tool-hook.sh:937` and `:524`, `session-end-hook.sh:466`), none of which
the list could ever have seen.

What to do instead: derive the set from the source -- every
`NAME="${REMEMBER_DIR}/tmp/..."` assignment is a marker, and every `> "$NAME"`
write must be guarded -- so a new marker is in scope the moment it is
declared, and the test fails on the omission rather than on the memory.

Cost to find: one release-audit round; the round-1 fix shipped with the gap
already in it, and the auditor's own exercise of the unguarded shape was what
made it a finding rather than an opinion.
