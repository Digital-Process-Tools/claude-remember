Writing a bare zero-width-space character (U+200B) as a Python string literal
via supertool's edit:@- TOML payload failed silently in an unhelpful way: the
literal character passed through the write but ruff then flagged it as
PLE2515 "Invalid unescaped character zero-width-space, use \\u200B instead" --
a legitimate finding, since Python itself treats an unescaped zero-width
character in source as a lint-worthy ambiguity.

What worked: falling back to a raw python3 -c string-replace pass to
substitute the literal char for the \\u200b escape sequence text, then
re-verifying with ruff check and python3 -c "import ast; ast.parse(...)"
directly, since the raw write bypassed supertool's own post-write validators.

Observed cost: one extra round trip (attempt via edit:@- with the literal
char inline -> ruff error -> manual python3 patch -> manual verification).
The lesson for next time: when a payload needs a zero-width or otherwise
invisible/ambiguous unicode character to land in Python source, write the
escape-sequence TEXT (the seven characters backslash-u-2-0-0-b) in the
payload to begin with, rather than typing the literal character into the
TOML source and letting ruff catch it after the write.

Not sure this is a rule worth promoting on its own -- it may already be
covered by more general "escape sequence vs literal character" guidance
elsewhere. Logging it anyway per the "hesitating because you are not sure it
is worth recording is the failure this removes" instruction.
