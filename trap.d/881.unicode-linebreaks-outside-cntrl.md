#881's fix for pipeline/log.py's log() flattens control characters
(`_CONTROL_CHARS = re.compile(r"[\x00-\x1f\x7f]")`, ASCII C0 + DEL) so a
message can't forge a second log line. The oss:auditor spawned during this
lane's self-review found a gap one step outside that range: Python's
`str.splitlines()` -- the same method the new regression test
(`tests/test_log.py::test_log_flattens_embedded_newline_to_prevent_forged_entry`)
uses to assert "no forged second line" -- also splits on U+0085 (NEL),
U+2028 (LINE SEPARATOR) and U+2029 (PARAGRAPH SEPARATOR), none of which the
new regex touches. A `message` containing one of those three codepoints
still reads as two lines to any Python (or line-oriented tool) consumer
that treats them as line breaks, even after the fix. Confirmed:
`python3 -c "print(len('safe malicious'.splitlines()))"` prints `2`.

This is not a regression introduced by the Python port -- the shell
precedent (`tr '[:cntrl:]' ' '` under `LC_ALL=C` in scripts/log.sh) has the
identical byte-wise blind spot, since none of those three codepoints'
UTF-8 encodings contain a C0/DEL byte. The Python fix mirrors the shell's
own gap exactly, as intended.

Ranked non-blocking at review time: grepping pipeline/ and scripts/ for
`splitlines()`/similar found no in-repo consumer that actually parses the
written log file this way (the only splitlines() call sites are
pipeline/consolidate.py:216 over a template string and
pipeline/spawn_guard.py:156 over an unrelated config file). So today it's
a rendering-seam gap, not an exploitable chokepoint -- but the attacker-
controlled surface the fix was written for (an untrusted error string from
pipeline/haiku.py) is exactly where it would be exercised if some future
consumer ever does read the log line-by-line in Python.

Unsure whether this is worth a dedicated jit-context rule or just a wider
regex someday (e.g. extending the character class, or sanitizing with
`str.splitlines()` boundaries directly rather than a fixed codepoint
range) -- logging it for /oss:curate to weigh rather than deciding here.
