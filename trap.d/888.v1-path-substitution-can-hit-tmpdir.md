`scripts/log.sh`'s `_remember_cfg_flatten_cache_path_v1()` and the inline
cleanup in `_remember_cfg_flatten_cache_publish()` both now derive the v1
(pre-#864) cache filename from the v2 one via `${_v2/-v2-/-}` / `${_f/-v2-/-}`
-- a plain bash first-match substring substitution, not anchored to the
filename's own slug segment. Both `_v2` and `_f` are full paths of the shape
`${TMPDIR:-/tmp}/remember-config-cache-v2-<slug>`, and `${var/pat/rep}`
replaces the *first* occurrence of `-v2-` anywhere in the string -- including
inside `$TMPDIR` itself, if that path happens to contain the literal
substring `-v2-` (e.g. a custom `TMPDIR=/mnt/build-v2-staging/tmp`).

Reasoned consequence (not reproduced): on such a `TMPDIR`, the substitution
fires against the `TMPDIR` segment instead of the `-v2-` the code means to
strip, producing a v1 path that does not match the real pre-#864 orphan
filename at all. The orphan cleanup this commit exists for then silently
misses the file it was meant to remove -- the same "best-effort, harmless
failure" class every other step in this function already tolerates, so
nothing crashes and no data is lost; the orphan just outlives the upgrade
that was supposed to clear it.

The pre-shrink code (`adf1d55`) did not have this exposure: it rederived the
slug independently from `$REMEMBER_DIR`, never touching `$TMPDIR`'s own text.

What would settle it: anchor the substitution to the known suffix instead of
a bare substring match -- e.g. operate on `${_v2##*/}` (the basename) rather
than the full path, so a `-v2-` inside `$TMPDIR` can never be the match.

Routing: if still open after a further audit, route through the ordinary
filing path per findings.md rather than staying a fragment.
