#1122's fix added a new helper, `_lock_file_inode()` (`scripts/lib-lock.sh`),
called twice per `_lock_try_steal` invocation (once before the rename, once
after a failed claim re-read) to compare inodes rather than content. Neither
call is wrapped in a timeout/watchdog the way `_lock_read_pid_timeout`'s own
`cat` is (SIGTERM/SIGKILL escalation, built because #1101/#1103 found a plain
blocking read in this exact code path can hang forever on a dataless/
cloud-sync placeholder or a wedged mount).

Self-review's Explore reviewer flagged this (observed, not reasoned-away):
`_lock_file_inode`'s own comment candidly calls the no-timeout choice
"reasoned, not reproduced" -- a metadata-only `stat()` syscall is believed
not to block the way an actual content `read()` can, but this is not
verified against a real wedged mount. It mirrors an already-shipped,
already-accepted pattern (`_lock_dir_age`, same file, same unguarded `stat`
shape, no watchdog either), so it is not a new risk *class* -- but it does
raise the number of unguarded, potentially-blocking filesystem calls inside
`_lock_try_steal` from one (`_lock_dir_age`) to three, in the one function
whose entire purpose is escaping a hung/stuck holder. On a filesystem where
`stat()` itself can block (a hard-mounted NFS server gone away, certain FUSE
mounts), this reopens -- in a new place, inside the steal path meant to
escape hangs -- the class of unbounded-blocking risk the watchdog elsewhere
in this file exists to close off, with no equivalent escape hatch for these
two new calls or for the pre-existing `_lock_dir_age` call either.

Not fixed in #1122 itself: wrapping `stat` in a watchdog would need the same
fork/background/SIGTERM-then-SIGKILL machinery `_lock_read_pid_timeout`
already carries, built fresh for a syscall this file's own existing code
(`_lock_dir_age`) already runs unguarded -- a materially larger change than
the inode-comparison fix #1122 asked for, and not clearly warranted without
a reproduced hang to point at (none exists for `stat()` specifically; only
for `cat`/`read()`, which is what the existing watchdog already covers).

Whether this is worth a `_lock_stat_timeout()` primitive generalizing
`_lock_read_pid_timeout`'s watchdog to any command, covering `_lock_dir_age`
and `_lock_file_inode` both in one pass, is a question for whoever curates
this fragment -- not decided here.
