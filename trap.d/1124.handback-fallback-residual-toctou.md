Second-pass self-review of #1124 (both Explore and oss:auditor, independently,
on the same follow-up commit) found that `_lock_handback`'s own fallback path
(`scripts/lib-lock.sh`, used when no content is known, or the noclobber write
already found something at the destination) is check-then-act rather than
atomic: `[ -e "${_dir}/pid" ]` then `mv "$_claim" "${_dir}/pid"`. A legitimate
writer landing in the few-instruction gap between the check and the `mv`
still gets clobbered -- narrower than the bare, unguarded `mv` this same
follow-up replaced (which clobbered unconditionally), but not zero.

Both reviewers ranked this `fails-to-preserve`, non-blocking, ship-behind-
trap.d. Closing it fully would need an atomic "create only if absent" write
for a case where this function does not have the content to write (that is
exactly why it falls to `mv` here rather than the noclobber `echo` used
elsewhere) -- there is no portable bash primitive for "atomically move a
file into a path only if that path is still absent" the way there is for
"atomically write new content only if the path is absent" (`set -o
noclobber`). The comment just above the fallback in scripts/lib-lock.sh
documents this explicitly as an accepted tradeoff, the same shape as the
pid-recycling and inode-portability limitations already documented
elsewhere in this file.

Worth a dedicated look if this residual window is ever observed to matter
in practice (it would need a legitimate writer to land in a gap measured in
shell instructions, immediately after this contender's own failed-or-
declined steal), but not solved under #1124's own time budget.
