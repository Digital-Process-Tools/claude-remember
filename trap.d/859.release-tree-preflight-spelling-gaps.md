Release audit for v0.38.0 (range v0.37.0..HEAD), class B finding, exercised against
`.github/scripts/check_release_tree.py`.

The new #859 preflight (`bash_grant_problem` / `_check_front_matter`, around lines 448-457
and 511-516) is meant to catch any shipped skill/command/agent whose `allowed-tools` grants
unrestricted shell, matching the directory's own ALLOWED_TOOLS_BROAD wording. Importing the
module and calling those functions directly against a set of spellings confirmed several
still pass the preflight silently:

- `allowed-tools: Read Bash` (space-delimited, no comma) -- the string is split only on
  `,`, so the single entry `"Read Bash"` never matches a bare-`Bash` check.
- `Bash(${CLAUDE_PLUGIN_ROOT}/../../../bin/bash:*)` -- the plugin-root prefix is trusted
  before the basename check runs, and a `..` segment inside the path is not refused.
- `Bash(bash5:*)` -- an unlisted bash binary name.
- Wrapper commands that can run arbitrary programs: `Bash(xargs:*)`, `Bash(sudo:*)`,
  `Bash(eval:*)`, `Bash(exec:*)`, `Bash(source:*)`, `Bash(find:*)`, `Bash(awk:*)`,
  `Bash(nohup:*)`, `Bash(timeout:*)`.

Positive controls fired correctly on the same run (bare `Bash`, `Bash(bash:*)`,
`Bash(/bin/bash:*)`, comma/YAML-list/flow-list forms of `Read, Bash`), so the check does
work for the spellings it was written against -- these are gaps in coverage, not a broken
check.

Ranked `misreports` by the release-auditor (non-blocking, trap.d-eligible). Latent only in
the tree released as v0.38.0: the only `allowed-tools` grants shipped today
(`skills/remember/SKILL.md:4`, `commands/doctor.md:3`) are both narrow
`${CLAUDE_PLUGIN_ROOT}/scripts/*.sh:*` forms that the preflight already handles correctly.
`tests/test_release_branch_preflight_851.py` has no space-delimited case and no `..` case
(read, not run). If promoted: split `allowed-tools` on whitespace as well as commas before
matching, refuse a `..` segment anywhere in a `Bash(...)` path, and extend the wrapper-
command list to cover the names above.
