Found by the release-auditor during the v0.42.0 release gate 3 audit (round 2,
range v0.41.0..HEAD), ranked `fails-to-preserve` (non-blocking, with a
possible upgrade -- see below) per skills/manager/phases/findings.md. Logged
as a trap.d fragment per that table's "can ship behind a trap.d fragment"
row. Related to #939, #942, #943.

`hooks.d/after_save/60-git-reconcile.sh:396` (`_grc_foreign_changes`): a
foreign write that gets *committed* (not merely written) while this slug's
rebase is stopped never shows up in `git status --porcelain`, so the #939
fix's own copy-and-restore logic never sees it. Exercised by the auditor:
another slug's `50-git-backup.sh`-style `git add -- other/ && git commit --
other/` succeeds against the detached HEAD left by a stopped rebase (`rc=0`).
The subsequent `git rebase --abort` then drops that commit from both the
branch and the working tree, and the hook's own notice still reports "the
tree is unchanged".

Ranked `fails-to-preserve` rather than `destroys` because a copy survives --
the dropped commit remains reachable from the `HEAD` reflog (observed:
`922d995`, reflog message `commit: auto-other`) -- but a reflog entry expires
and nothing else points at it, so if the maintainer judges an expiring,
otherwise-unreferenced reflog entry as "no copy" for this table's purposes,
this row is `destroys` and blocks a release the same way #942/#943 do.

What would settle it: compare `HEAD` immediately before the abort against
what the stopped rebase had picked, and keep (e.g. cherry-pick forward, or
refuse to abort and surface) any commits on that HEAD that are not the
rebase's own.

Routing: if still open after a further round, route through the ordinary
filing path per findings.md rather than staying a fragment -- and reconsider
the blocking classification per the note above before doing so.
