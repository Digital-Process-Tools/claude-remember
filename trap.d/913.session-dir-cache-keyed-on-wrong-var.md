Found by the release-auditor during the v0.42.0 release gate 3 audit (range
v0.41.0..HEAD, round 1), ranked `fails-to-preserve` (non-blocking) against the
findings table in skills/manager/phases/findings.md, logged here rather than
filed per that table's "can ship behind a trap.d fragment" row.

`scripts/post-tool-hook.sh:528-567` (#913/#923, the SESSION_DIR cache) keys
the cache on `MEMORY_PROJECT_DIR`, but the cached value is computed from
`$PROJECT` (`session_dir_slug "$PROJECT"`, :553). `lib-memory-dir.sh:95-100`
(#56) makes `MEMORY_PROJECT_DIR` the same for every worktree of a repo, while
`PROJECT_DIR` deliberately stays the worktree path "so session recovery still
finds transcripts under the worktree slug". Two features that are each
correct on their own combine badly: worktree B can get worktree A's cached
`SESSION_DIR`.

Effect: on the path with no stdin `transcript_path` (:606-610, :683-687 --
older CLIs and non-Claude-Code hosts), B's tool calls pick up A's newest
transcript. B's sessions are not captured, or A's are driven twice, with no
warning because A's directory exists.

`tests/test_session_dir_cache_913.py` has no worktree case (grep for
"worktree": 0 hits) and is skipped on Windows, which is the platform the
change targets.

What would settle it: two linked worktrees, hook stdin without
`transcript_path`; check whether B's SESSION_DIR resolves to A's slug.

Fix direction: key the cache on `$PROJECT`, the value the computation
actually reads, rather than on `MEMORY_PROJECT_DIR`.

Routing: per findings.md, if this is still open after a second round it goes
through the ordinary filing route rather than staying a fragment.
