Ran `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/tree_snapshot.py" snapshot >
before_snapshot.txt` from inside the worktree in one Bash call, then in a
LATER, separate call ran `cat before_snapshot.txt | python3
".../tree_snapshot.py" compare --before -` without a `cd` on that same call.
The Bash tool's cwd had reset to the main clone (per its own "cwd resets
between bash calls" note) by the time the compare call ran, so `compare` read
the main clone's git state (still at the pre-lane base commit,
8bd5434...530) instead of the worktree's (878be13..., my own committed diff),
and reported `VERDICT: mutated -- HEAD moved from 878be13... to 8bd5434...`.

This is exactly the failure mode the developer brief and review.md warn about
for every OTHER write in this flow (note/report/PR payload all need `cd
<worktree_root>` on the same line as the write) -- it was not obviously
covered for a read-only diagnostic invocation like `tree_snapshot.py
compare`, which has no explicit "same call as the cd" instruction in
review.md the way the write-ops instructions do. Cost: one wasted call, plus
several seconds of genuinely believing a spawned reviewer (Explore, which
still has Bash) had mutated the tree, before re-running the compare with an
explicit `cd` on the same line and getting `clean`.

Confirmed by: re-running `cd <worktree> && git rev-parse HEAD` in one call
and seeing the correct HEAD (878be13...), then re-running the compare
command with `cd <worktree> && cat ... | tree_snapshot.py compare ...` in a
single call and getting `VERDICT: clean`.

Possible generalization (not decided here, for the curator): every
multi-step verification sequence that pipes a file into a script -- not just
the three named write ops -- needs the same "same call as the cd" framing
review.md gives to write ops, or a snapshot/compare pair silently reads the
wrong repo and produces a false-positive "mutated" verdict that looks
exactly like a real one.
