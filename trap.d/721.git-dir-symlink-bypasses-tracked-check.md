Observed during the first review round over #720/#721's fix (oss:auditor, against
`_remember_handoff_is_tracked` in scripts/session-start-hook.sh), and re-confirmed on the second
round without a fix being attempted -- flagged as a `could-not-check` residual rather than dropped,
and this fragment is the receipt the PR body's own residual item names.

`_remember_handoff_is_tracked` decides whether `.remember/remember.md` is tracked by asking git,
scoped to `$PROJECT_DIR`: `git -C "$PROJECT_DIR" ls-files ...` (and the case-insensitive fallback,
`git -C "$PROJECT_DIR" ls-files -z`). Both resolve `.git` the ordinary way -- following
`$PROJECT_DIR/.git`, which can itself be a symlink (or, on a real git worktree, a file pointing
elsewhere via `gitdir:`).

If `PROJECT_DIR/.git` pointed at a DIFFERENT repository's git directory -- one the attacker
controls, with its own object database and index, entirely independent of what the user actually
committed -- both the exact-case check and the case-insensitive fallback would answer against that
attacker-controlled index rather than the real one. A `.remember/remember.md` the real repository
never tracked could then be reported "untracked" (safe to deliver) by a git call that is, in fact,
answering a question about a different repository's history.

**Why this was not fixed under #721's own threat model.** The finding requires the attacker to
have ALREADY replaced `PROJECT_DIR/.git` itself (or planted a `.git` file with a `gitdir:` pointer)
-- a strictly stronger local-write primitive than "untrusted content reached the session's own
context" (a Read of a hostile file, a fetched page, a repo the victim merely cloned and opened),
which is the precondition #720/#721 assume throughout. An attacker who can already rewrite
`PROJECT_DIR/.git` can already write anything else in the working tree too, including
`.remember/remember.md` itself directly -- at which point the tracked-check is not the weakest
link.

Whether this is worth hardening anyway (e.g. refusing to trust the tracked-check at all when
`PROJECT_DIR/.git` is a symlink, or resolving and logging the real gitdir target first) is a
judgement call for /oss:curate or a maintainer decision, not something this lane settled. The
existing sanitisation in this same function (`unset GIT_DIR GIT_WORK_TREE GIT_INDEX_FILE`) defends
against a LEAKED env var pointing elsewhere; it does nothing for a `.git` FILE/symlink that already
points elsewhere before the process starts.
