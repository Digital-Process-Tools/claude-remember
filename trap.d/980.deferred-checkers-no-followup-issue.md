# PR #988 (closes #980): two deferred checkers claim "filed for a follow-up" with no issue to show for it

`_check_catch_all_in_loop` and `_check_single_line_delegate_positional` in
`.github/scripts/check_release_tree.py` were deliberately left out of #980's
`_iter_non_heredoc_lines` migration (one has its own multi-line state
machine that would need interleaving rather than wrapping; the other filters
an already-extracted function-body string, not the raw file by line number).
Both still carry the exact same unguarded `line.lstrip().startswith("#")` /
`ln.lstrip().startswith("#")` comment test #919/#980 fixed everywhere else,
so a heredoc body line could still be misread the same two ways: a `#`-led
body line read as a real comment, or a body line containing literal
`while`/`for`/`until`/`done`/`*)` (or a positional-splice shape) text read as
real code.

Both in-code docstrings added by #988 say "filed for a follow-up rather than
fixed silently alongside the other 16." Checked at review time
(`gh-issues:search=catch_all_in_loop`, `gh-issues:search=single_line_delegate`,
`gh-issues:search=heredoc,state=open`): no such issue exists. The only open
issue matching is #980/PR #988 itself, which this PR closes. So the docstring
sentence currently describes an issue that was never opened, rather than
pointing at a real one.

Ranked against `skills/manager/phases/findings.md`'s table: this is a
checker that can misreport (false positive/negative on a heredoc-body line),
not a destructive/disclosing/containment-breaking/forging/host-baked defect
-- `misreports`, which the table routes to "can ship behind a trap.d
fragment," not an immediate issue. Recorded here rather than filed, since
the defect class itself (comment-vs-heredoc-body ambiguity in a shell-shape
checker) is not new -- #919/#980 already exist for it -- and these two
functions are the two intentional holdouts, not a silently missed third
instance of the same bug.

What would settle it: either open a small follow-up issue naming these two
functions specifically (so the docstrings' claim becomes true), or soften
the docstring wording to "not yet fixed" rather than "filed for a
follow-up" until one actually is.
