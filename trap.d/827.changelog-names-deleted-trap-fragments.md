#827 (finding 1 of 3, carried forward from the v0.35.1 release audit round 3):
CHANGELOG.md prose permanently names a `trap.d/NNN.*.md` fragment file by path,
but a later curate pass can delete that same fragment once it is promoted into
a jit-context rule (or declined) -- and nothing keeps the two in sync.

Observed at HEAD (fix/827, based on origin/main @ e994e0f): `CHANGELOG.md:72`
says "Fixed (#822): `trap.d/804.edit-op-defaulted-to-main-clone-not-worktree.md`
no longer names this maintainer's actual local checkout paths" and
`CHANGELOG.md:25` says "...closing one of the three edges logged to
`trap.d/745.entrypoint-sniff-has-two-unfixed-edges.md` (#803)." Neither file
exists in the tree: `git ls-files trap.d` at HEAD returns neither name. The
first was deleted by commit 7b297fd (PR #817, curate); the second by a later
commit (aa37372). Confirmed with `grep -r <name> trap.d/` returning 0 hits for
both.

The mechanism: `changelog.d/*.md` fragments are written by a PR that fixes a
trap.d-logged defect, and those fragments get folded into CHANGELOG.md and
deleted at release time (this is by design, per
`.claude/jit-context/paths/00-manual/changelog-fragments.md`). Separately,
`trap.d/*.md` fragments get folded into jit-context rules (or declined) and
deleted by a later, independent curate pass. When a changelog fragment's prose
names a trap.d file by path -- which is the natural thing to write, since the
trap.d file IS the record of the defect being fixed -- and a curate pass later
deletes that trap.d file, CHANGELOG.md silently ends up asserting the
existence of a file that is gone. This is not a one-off: it will recur any
time a PR's changelog entry names a trap.d file that a later curate round
also handles, and there is no check enforcing referential integrity between
the two artifacts (neither `assemble_changelog.py --check` nor `--check-links`
looks at trap.d/ at all -- confirmed by reading `.oss/assemble_changelog.py`'s
own two check modes, which only validate fragment shape and version-link
references).

Cost if uncorrected: a reader who follows a "Fixed" changelog entry's own
trap.d citation to understand what was fixed hits a 404/missing-file, on a
release note that is otherwise still accurate. Non-blocking (per the release
audit's own ranking, all three of this round's findings shipped in v0.35.1
under the two-round carry-forward cap) -- but it is a real, recurring
authoring trap, not a one-off cosmetic slip.

What is NOT decided here, deliberately: whether to (a) retroactively edit
published CHANGELOG.md prose when its cited trap.d file is later deleted, (b)
change changelog-fragment authoring convention to describe the mechanism in
prose without a raw trap.d path (so nothing to go stale), or (c) add a
referential-integrity check as a new CI leg or curate-time step that flags a
changelog reference to a trap.d file the tree no longer has. Each is a real
design call with its own cost (a) rewrites history and could disagree with a
tagged release's own frozen CHANGELOG; (b) loses a genuinely useful pointer
for the common case where the trap.d file still exists; (c) adds a new check
surface. Left for whoever curates this fragment to decide, holding it
alongside whatever other authoring-convention fragments exist at the same
time.
