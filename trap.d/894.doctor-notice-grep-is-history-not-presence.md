Release audit (v0.39.0, round 1, oss:release-auditor) found that doctor.sh's section 6c
(scripts/doctor.sh:1028-1066, added by e0cbc3c/#894) decides "legacy recovery-token config
in use" by grepping every logs/memory-*.log for a `NOTICE:` substring and keeping the
last match, rather than checking current presence the way pipeline/haiku.py itself does.

Two failure directions, both reasoned from reading the code rather than from running it:

- **Stale warning after migrating.** A user who removes the legacy `REMEMBER_OAUTH_TOKEN`
  or `haiku.oauth_token` keeps getting `WARN ... REMEMBER_OAUTH_TOKEN is set but is no
  longer read` until rotate_logs archives the old log -- more than 7 days
  (scripts/log.sh:1912).
- **False "all clear".** It prints `OK   No legacy recovery-token config in use` whenever
  the logs contain no NOTICE. But `haiku.py:_inject_configured_oauth_token` returns early,
  before either legacy check, whenever the host supplies `CLAUDE_CODE_OAUTH_TOKEN`. On
  those hosts a still-set legacy value is never logged, so doctor reports OK while it is
  in fact set.
- The match is also unanchored: bare substring `NOTICE:`, not `[haiku] NOTICE:`.
- `tests/test_doctor_deprecated_oauth_860_notice.py` has no case for "an old NOTICE in an
  older log, the legacy value since removed."

Ranked `misreports` (non-blocking) against skills/manager/phases/findings.md's table --
an absence the doctor's own grep-of-history approach produces, read as a fact about
current state. What would settle it: whether doctor should check presence directly (the
same boolean checks haiku.py uses) instead of reading log history.
