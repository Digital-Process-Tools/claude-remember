#1011 gate-3 round-1 audit finding (non-blocking, misreports): the below-threshold
no-save path in scripts/post-tool-hook.sh regressed in process count while this range own
changelog/docs claim an improvement, and the "2 processes" wording does not match either
path.

Observed by the oss:release-auditor spawn auditing v0.42.4..HEAD (dispatch token
82fd2f9bb272), not reproduced by me directly -- reported here on the auditor own
measurement, which extracted both trees with git archive and counted PIDs around one hook
call (minimum of 9 runs each):

- /bin/bash 3.2.57: below-threshold path went from 6 to 9 total processes; cooldown path
  went from 8 to 5.
- Homebrew bash 5: below-threshold 6 to 9; cooldown 7 to 4.
- xtrace (PS4 on BASH_XTRACEFD) names the six new processes on the below-threshold path:
  the _pt_scan_lines subshell, the tail list subshell, tail itself, the printf-then-wc
  subshell, printf, and wc -- replacing v0.42.4 single wc -l < file read.

Where: scripts/post-tool-hook.sh ~L1017 and L940-971 (the _pt_scan_lines call wrapped in a
command substitution, the tail-then-printf chunk read, and the printf-piped-to-wc line
count); also tests/spawn_counting.py COUNTED list (counts only execd binaries, so it cannot
see a bash subshell fork at all -- which is exactly what #1011 own docs/windows.md says
leaks a kernel Token on Windows 11 25H2 per fork); also changelog.d/1011.fixed.md and
1017.fixed.md, whose "4 or 5 spawns to 1" / "to 2" wording undercounts both paths: execd
counted binaries are 2 (tail, wc) below threshold and 1 or 0 in cooldown, but total
processes created (forks included) are 9 and 5 on bash 3.2.

What it cost: nothing yet -- caught before the tag, in gate 3 round 1. The number and claim
would otherwise have shipped in this release changelog and docs/windows.md own framing of
what the release reduces.

How it was confirmed: the auditor positive control -- the same PID-delta method shows the
cooldown path dropping by 3 processes, so the method detects change in both directions, and
the below-threshold regression is a real effect and not a measurement artifact. Windows-side
severity is reasoned, not observed (MSYS fork creates a Windows process per the range own
docs; no CI leg observes it directly -- every post-tool hook test module blanket-skips on
win32 per docs/windows-skip-triage.md).

Suggested fix, left to whoever promotes this: have _pt_scan_lines set globals instead of
being called inside a command substitution, avoid the tail-then-printf-then-wc pipeline for
the below-threshold path, and correct the changelog/docs wording to "external commands" (or
name the real total including forks) rather than "processes", split by path
(below-threshold vs. cooldown) since they now move in opposite directions.

Ranked: misreports (release.md / findings.md ranking table) -- can ship behind this
fragment, not on the critical path. Round 1 of gate 3 still stops the tag by the
round-one-always-stops rule; this fragment is what lets round 2 treat it as carried forward
rather than re-filed as an issue.
