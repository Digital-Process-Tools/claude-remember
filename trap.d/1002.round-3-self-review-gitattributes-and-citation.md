#1002 round 3 self-review (PR #1010, branch fix/1002-real-wscript-evidence): two
non-blocking findings from the oss:auditor pass, neither fixed in this round.

1. No `.gitattributes` pins the vendored `tests/fixtures/v0_42_3/` files
   (`lib-detach.sh`, `lib-detach-pidwrap.sh`, `windows-hidden-run.vbs`) against line-ending
   rewrite on checkout. `tests/fixtures/v0_42_3/NOTE.md` states the entire point of these
   files is to stay byte-for-byte identical to the `v0.42.3` tag forever; the auditor
   confirmed the committed blobs are correct (byte count matches `git show v0.42.3:...`
   exactly) but could not inspect the `windows-latest` runner's own `core.autocrlf` value
   (no shell access to that runner). What makes this worth a row rather than purely
   theoretical: the three tests against these fixtures are `xfail(strict=True)`, which
   only requires *a* failure, not *the documented* failure -- if a future checkout-config
   change ever did corrupt these bytes (e.g. CRLF conversion), the resulting DIFFERENT
   failure would likely still satisfy the existing xfail markers, so CI would keep
   reporting green/xfailed with no signal that the fixture's byte-identity invariant had
   silently broken. Fix, if taken: add a `.gitattributes` entry forcing these three paths
   to `-text` (no line-ending conversion) and/or a cheap CI step comparing their checked-
   out byte count/hash against the committed value before the xfail tests run.

2. `docs/windows.md`, both `trap.d/1002.*.md` fragments, and the `xfail(strict=True)`
   `reason=` strings in both real-wscript test modules all cite "run #38049234152, jobs
   114204833302/.../114204833202" as the OBSERVED evidence for the v0.42.3 traps. That run
   is accurate (verified line-for-line against the raw log) but is also the SAME run that
   had the two test-isolation bugs (TMPDIR cache leak, repo-mutation-guard trip) a second
   commit on this PR fixed -- a cleaner confirming run exists on the same PR head (run
   #38051416393, e.g. job #114211139437: "3 xfailed", no unrelated failures) and nothing
   was updated to cite it alongside the contaminated one. Not a functional defect -- the
   cited lines are verbatim accurate -- but a future reader diffing the citation against
   that job's full log will also see the two unrelated isolation-bug failures mixed in
   with the genuine trap evidence, with nothing pointing them to the clean follow-up run.

Ranked `fails-to-preserve` (1) and `misreports` (2) per the release-ranking table; both
non-blocking, ships behind this fragment rather than filed, for /oss:curate to triage.
