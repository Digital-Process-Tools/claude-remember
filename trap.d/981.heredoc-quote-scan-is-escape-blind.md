#981's `_in_quotes_before` (`.github/scripts/check_release_tree.py`) matches only
COMPLETE single/double-quoted spans on a line to decide whether a `<<WORD`-shaped
substring sits inside an ordinary quoted string rather than opening a real heredoc.
It has no backslash-escape awareness at all.

Observed by the self-review auditor against commit ba1e4b1: for a line like
`echo "it is \" <<EOF"` (a backslash-escaped quote inside a double-quoted shell
string), the regex-based span match ends at the FIRST `"` character it sees after
the opening one -- it does not know that the backslash in front of it means "this
is not really a closing quote". So the span closes one character too early, the
`<<EOF` substring that follows lands outside any matched span, and
`_in_quotes_before` reports it as NOT in quotes. The heredoc tracker then opens for
a line that was never a real heredoc opener -- silently going into "heredoc body"
mode for content that is not heredoc body at all, which is the exact failure
direction (silently swallowing real content) #981 itself was filed to eliminate,
just reached by a different trigger (an escaped quote rather than an unescaped
comment or substring).

Confirmed this is NOT a regression introduced by the quote-awareness fix itself:
the SAME line produced the SAME wrong answer (not-in-quotes) against the original
naive quote-TOGGLE implementation that preceded the complete-span rewrite -- the
toggle also closes on the escaped quote character, with no escape awareness
either. So this is a pre-existing limitation of "detect quoting via a cheap regex
heuristic, no real shell escape/quote parsing", not something this fix made worse.

Ranked (ranking table in skills/manager/phases/findings.md) as `misreports`,
non-blocking -- can ship behind this fragment rather than block #981's own fix.
Not fixed in #981 because real backslash-escape-aware shell quote parsing is a
materially bigger piece of work than the comment-skip and apostrophe-false-
negative fixes #981 actually needed, and risks its own new edge cases (nested
escapes, `$'...'` ANSI-C quoting, etc.) for a guard this file's own existing
conventions (`_mask_arithmetic`, `_HEREDOC_OPEN`'s own quote-shape handling)
already treat as "a cheap heuristic, not a parser".

Also noted by the same auditor pass, same root cause, lower severity and NOT
logged as its own finding: `_in_quotes_before`/`_HEREDOC_OPEN` only look for ONE
heredoc-opener-shaped match per line (`.search()`, not `.finditer()`), so a line
with two such shapes where the first is correctly recognized as quoted never
looks for a second, real opener later on the same line (e.g.
`echo "look at <<EOF" && cat <<REAL`). This lands in the SAFE direction (the
tracker just never opens for the second, real one, so nothing is swallowed) --
a missed-but-safe detection gap, not a defect worth its own row.

If a real need for escape-aware quote detection shows up again (a second,
independent report against this same function), that is the point to either
hand-write a tiny escape-aware scanner or accept the cost of a real shell
tokenizer -- doing it preemptively from one observed edge case, never exercised
by any file currently shipped in this repo, was judged not worth the risk of a
regex that is itself subtly wrong in a new way.
