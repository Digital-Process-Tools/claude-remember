scripts/log.sh:69-71 (`_remember_log_dir_unsafe`) and scripts/post-tool-hook.sh:392-396
(`_remember_dir_is_unsafe`), together with scripts/resolve-paths.sh:222-252
(`_remember_normalize_win_path`) and scripts/lib-memory-dir.sh:160-173
(`_resolve_remember_dir`): `_remember_normalize_win_path` only rewrites drive-letter and
`/c/`-style forms, so a native UNC project dir (`\\server\share\proj`) reaches
`_resolve_remember_dir` unchanged. With the default relative `data_dir`, REMEMBER_DIR
becomes `\\server\share\proj/.remember` -- a value neither new #902 guard function
recognises as safe (both treat anything not `/`-prefixed and not drive-lettered as
unsafe). Verified on macOS bash by copying both guard functions verbatim: a value like
`\\srv\share\p/.remember` comes back UNSAFE from both. Reasoned, not observed, for
Windows/Git Bash: a user with a UNC/network-share project dir would get every daily log
sent to /dev/null and every autosave refused (post-tool-hook.sh:947-949), compounding
with the already-logged swallowed-FATAL finding so no trace of the refusal survives
anywhere. At v0.40.0 this path went straight to `mkdir -p` instead, which presumably
worked -- this is new fallout from #902's own guard, not a pre-existing gap. The repo
already handles UNC paths elsewhere (lib-slug.sh:228-256, `\\?\UNC\`); the new test's
accepted-path list (tests/test_remember_dir_guard_902.py:379) has no UNC case, and the
windows-latest CI leg (.github/workflows/tests.yml:33,:101) exercises no UNC project dir
either, so this gap is uncovered. What would settle it: one Git Bash run with
CLAUDE_PROJECT_DIR set to a UNC path on v0.40.0 and on HEAD, comparing whether
`.remember/logs/` and a save log appear in each.
