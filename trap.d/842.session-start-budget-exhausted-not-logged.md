Release audit for v0.38.0 (range v0.37.0..HEAD), class A finding, found by reading, not
exercised.

`scripts/lib-memory-context.sh:1342-1350`, inside `_remember_apply_session_start_budget`:
the function drops archive -> today -> recent -> now in priority order while the body is
over `thresholds.session_start_max_bytes`. If it is still over budget after the loop
exhausts every droppable section, it calls `printf -v` and returns with no check of
whether the budget was actually met and no log line either way.

Likeliest trigger: a handoff alone that is already over budget by itself -- the handoff is
never cut, and it is delivered in full for the first `handoff_max_redeliveries` deliveries.
A caller in that state sees every memory file dropped and listed, the body still crossing
Claude Code's own preview threshold, and a daily log that reads exactly as it would if the
budget had been met. There is no way for an operator to tell "budget satisfied" from
"budget exhausted, still over" from the log alone.

Ranked `misreports` by the release-auditor (non-blocking, trap.d-eligible rather than a
design change worth widening #845's diff for). Not verified against a live over-budget
handoff -- reasoned from the script's own control flow after line 1349, not observed. If
real, the fix is a comparison of the final `_head_len + ${#_mem}` against `_max` after the
drop loop, with a loud log line (not a failure) when it is still over.
