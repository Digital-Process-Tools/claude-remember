Found by the release-auditor during the v0.42.0 release gate 3 audit (round 3,
range v0.41.0..HEAD), ranked `misreports` (non-blocking) per
skills/manager/phases/findings.md. Logged as a trap.d fragment per that
table's "can ship behind a trap.d fragment" row. Related to #939, #942, #943,
#946.

`hooks.d/after_save/60-git-reconcile.sh:404` and `:490-500`: `_grc_foreign_changes`
hides a failed `git status --porcelain` call behind `2>/dev/null`, piped
straight into a `while` loop -- an empty result from a failed call reads
identically to a genuinely clean tree, and the hook then reports "aborted,
the tree is unchanged" with no basis for that claim. Separately, if
`git rebase --quit` itself fails and the subsequent
`_grc_rebase_in_progress` check happens to return false anyway, the hook's
notice says "the rebase state was cleared" -- a claim that was never actually
checked, only inferred from one more git call that itself was not verified.

The auditor's own re-assessment agrees with the developer lane's own
`below-bar` disposition on these two in isolation (both need `git` itself to
fail transiently at a point where several other git calls against the same
repo just succeeded moments earlier) -- logged here primarily because the
SAME wrong-attribution pattern was separately observed firing for real in
round 3's other scenarios (see #946 and the trap.d fragments for F2/F3): the
notice claims a tree state ("only $SLUG was reset", "the tree is unchanged")
that nothing in the hook actually verified, independent of whether the
underlying git call failed or merely did something the hook did not expect.

What would settle it: whether the log/notice text may ever claim a tree
state that nothing in the hook explicitly checked.

Routing: if still open after a further audit, route through the ordinary
filing path per findings.md rather than staying a fragment.
