Observed during self-review of #1051 (scripts/lib-memory-context.sh, the
_remember_apply_session_start_budget / _remember_start_cache_context_load
marker-file handshake).

The marker file (REMEMBER_DIR/tmp/start-context.served-bytes.$$) carries a
small decimal byte-count written by one function and read by another. The
read side validates "all digits" and bounds-checks the arithmetic, but
nothing checksums or length-prefixes the content. A write torn by a
disk-full condition mid-write (e.g. a real value "1234" truncated on disk
to "12") still parses as all-digits and passes every guard, producing a
plausible-but-wrong head/tail split with nothing logged -- silently wrong
rather than falling back to the existing conservative "give up, warn,
inject untrimmed" path. Narrow precondition (disk-full exactly mid a 1-4
byte write) and the existing fallback already exists for the "no marker"
case, so this was judged non-blocking rather than something to fix inline.

What would close it: a trailing newline or fixed-width field the reader can
use to detect a short read (length != expected cursor position), or a
second guard requiring the parsed value to be no larger than what the
largest plausible memory store could produce (sanity-bound the count, not
just its shape).
