Release audit for v0.42.3 (round 1, gate 3) flagged scripts/detect-tools.sh:296
(receipt at :330-331).

What was observed: the versioned fallback ladder is `python3.{13..9}` -- it never
tries python3.14 or newer, even though the comment at :289-295 says the ladder
starts at "the newest released Python" and 3.14 has already shipped. Reproduced
in a scratch dir with stub `python3` = 3.8.10, `python` = 2.7.18 and
`python3.14` = 3.14.0 all on PATH and the tools cache off: sourcing
detect-tools.sh exits with
`FATAL: below the floor this plugin supports:python3 Python 3.8.10python Python 2.7.18`
even though a supported interpreter (python3.14) is on PATH. Positive control:
renaming the stub to `python3.13` gives `rc=0 PYTHON=python3.13`, so the ladder
mechanism itself works -- it just stops one version too early.

Two related, smaller problems in the same receipt: `_bl` runs its entries
together with no separator (visible in the FATAL message above, which runs two
tool names and versions together with no newline/comma); and the not-found
branch prints `found $PATH$_pr` with no label and has dropped the Microsoft
Store / exit-49 guidance the #650 receipt used to give.

What would settle the real fix: whether the ladder's top should be derived from
`_remember_run_python`'s own generic `python3.[0-9]*` glob arm instead of a
fixed `13`, so a newer interpreter doesn't need a code change every October.

Ranked `misreports`, non-blocking per the release-3 ranking table -- logged here
rather than filed, for /oss:curate to triage.
