`gemini-cli` 0.57.0's cached OAuth credentials (`~/.gemini/oauth_creds.json`, from an earlier interactive `gemini` login) had a `refresh_token`, but a real invocation still failed to use it: `gemini -p "say hi" --output-format text` prompted `Opening authentication page in your browser. Do you want to continue? [Y/n]` even though credentials existed on disk. Answering `Y` (with `--skip-trust` and `GEMINI_CLI_TRUST_WORKSPACE=true` both set, to rule out the trust prompt as the blocker) printed `Cached credentials are not valid: invalid_grant`, then hung waiting for an OAuth browser-redirect callback with no manual/OOB code ever printed, even with `--debug`. Answering `n` instead produced a clean `FatalCancellationError: Authentication cancelled by user.`, so the browser prompt is the actual gate, not a side effect of something else failing first.

Cost: roughly 20 minutes across several `gemini` invocations (varying `--skip-trust`, `GEMINI_CLI_TRUST_WORKSPACE`, `-d`/`--debug`, response to the Y/n prompt) before concluding no live Gemini CLI session can be driven from this kind of headless environment without either a human refreshing the OAuth token interactively (with a real browser) or a `GEMINI_API_KEY`/`GOOGLE_API_KEY` provisioned in the environment -- neither of which was available. Confirmed there is no unauthenticated escape hatch: even `gemini --list-extensions`, which reads local config only, hits the same auth path before it can answer.

Not confident this is a durable rule (an expired/never-issued token is a one-off state, not a code path), but worth surfacing in case future Gemini-CLI-related lanes hit the identical wall and waste the same 20 minutes rediscovering it. Filed as issue #532 rather than solved here.
