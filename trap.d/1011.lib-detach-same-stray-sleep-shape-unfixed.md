While fixing #1011's doctor.sh watchdog (fork-to-pidfile-write race fixed in a follow-up commit on the same branch after a reviewer found it empirically), both the reviewer and the auditor independently noted that scripts/lib-detach.sh's own Windows-save watchdog (_remember_detach_windows_impl, the `( sleep "$_watchdog_secs"; kill -9 "$wscript_pid" 2>/dev/null ) >/dev/null 2>&1 &` subshell) has the identical "kill the subshell, not the sleep child it already forked" shape -- with no PID-handoff mechanism at all, so a fast wscript.exe exit there can orphan its own `sleep` for up to the full 15s bound, exactly the class of leak this branch's second commit closed in doctor.sh.

Not fixed here: the #1011 task's explicit audit scope for lib-detach.sh was the FULL-BOUND BLOCKING bug (the fd-inheritance issue that made every probe cost ~2x its bound), and lib-detach.sh is confirmed NOT affected by that one (it already redirects its own stdout/stderr, from an earlier #1002 round, and all 24 of its existing stub-driven tests return well under 1.5s against its own 15s bound). The stray-sleep-on-early-exit concern is a separate, lower-severity issue (self-heals within the bound, holds no fds since they are already redirected) that was never part of this task's scope, and lib-detach.sh is called on EVERY Windows save (a much hotter path than doctor.sh's on-demand probes), so a fix there carries more regression risk than the budget of this already-two-commit branch could absorb safely.

Logged rather than fixed or filed as a tracked issue: it is the same class as what the second commit on this branch just closed, reachable (every Windows save), but non-blocking and not part of the assigned task -- the shape findings.md's own ranking table calls "can ship behind a trap.d fragment" rather than "report-for-filing."
