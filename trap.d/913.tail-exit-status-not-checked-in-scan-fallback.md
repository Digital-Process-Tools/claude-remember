#913: `_pt_scan_lines`'s fallback-to-full-recount branch cannot distinguish "the
transcript genuinely shrank or was rewritten" from "the `tail -c +OFFSET` read
transiently failed" (an EPERM, a mid-read I/O error, or a delete/rotate race
between the hook's earlier existence check and this read). Both cases produce
the identical signal the self-healing check looks at: an empty `_chunk`, or a
first byte that is not the expected newline.

Observed by the `oss:auditor` self-review spawn on PR #913's own diff, not
reproduced live -- the trigger (a transient read failure on a file that
exists and is otherwise healthy) is narrow and was not constructed in a test.

Consequence if it fires: the sidecar is reset to `(0, 0)` and `CURRENT_LINES`
is reported as `0` for that one call, same as a genuine empty-growth call. The
auditor's own assessment: self-healing (the next call does a fresh full
recount from offset 0, which is correct), so the cost is one wasted full scan
plus a silently-wrong `DELTA` for the single affected call -- never a crash,
never a false "save fired," and ranked non-blocking.

`tail`'s own exit status is masked today: `_chunk=$(tail -c +"$_start" "$_file"
2>/dev/null; printf 'X')` -- the command substitution's exit status is
`printf`'s (always 0), and `printf 'X'` has to run inside the same
substitution as `tail` to preserve a trailing newline through `$()`'s own
newline-stripping, which is why the two are combined in the first place.
Capturing `tail`'s own status separately (e.g. appending its `$?` into the
sentinel and parsing it back out, or checking `[ -r "$_file" ]` before
trusting an empty read as "shrank," per the auditor's own suggestion) would
need to thread through the same sentinel-preservation trick without
reintroducing the problem it solves. Left to the curator: whether this is
worth the added complexity for a self-healing, narrow-trigger case, and if
so, which of the auditor's two suggested shapes fits best here.
