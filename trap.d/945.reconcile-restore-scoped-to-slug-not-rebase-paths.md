Found by the release-auditor during the v0.42.0 release gate 3 audit (round 3,
range v0.41.0..HEAD), ranked `fails-to-preserve` (non-blocking, possible upgrade
-- see below) per skills/manager/phases/findings.md. Logged as a trap.d fragment
per that table's "can ship behind a trap.d fragment" row. **This is a regression
introduced by commit 84a6ea5 (#945)**, the same commit this round's gate audits.
Related to #939, #942, #943, #946.

`hooks.d/after_save/60-git-reconcile.sh:445-452,466-468`: the scoped restore the
#943 fix introduced assumes every commit this run's rebase could have replayed
is confined to this run's own `$SLUG/`. That is false -- the ahead/behind commit
set can include OTHER slugs' commits from either machine, and the rebase has
already moved those paths before the scoped checkout/rm only restores `$SLUG/`.

Reproduced by the auditor against real scratch stores in three shapes:
- no concurrency at all: another slug's content ends up reverted and staged
  after the scoped restore, then silently dropped on that slug's next ordinary
  save;
- a conflict in the OTHER slug (not this run's own): that slug is left with
  live `UU` conflict markers in a real memory file, and the hook's own notice
  claims only `$SLUG` was reset;
- upstream content for another slug left staged on top of local HEAD.

Why ranked `fails-to-preserve` rather than `destroys`: the lost content still
exists in a local commit in history (not discarded outright the way #939/#942/
#943 were). If the maintainer counts "only reachable via history, behind a
later commit that removed it from the tree" as equivalent to "no copy
anywhere", this row is `destroys` and blocks a release.

What would settle it: scope the restore to the paths the rebase actually
changed (a diff of ORIG_HEAD against the index/tree), not to `$SLUG` -- the
same fix direction likely closes #946 (F3 in the round-3 report) too, since
both are mis-scoped relative to what the rebase actually touched.

Routing: if still open after a further audit, route through the ordinary
filing path per findings.md rather than staying a fragment, and reconsider
the blocking classification per the note above before doing so.
