Observed on the second review pass over #720/#721's fixup commit (scripts/session-start-hook.sh's
new `_remember_th_ci_eq`, duplicated from `scripts/lib-case-divergence.sh`'s existing
`_remember_case_fold_eq` for a reason stated in its own comment -- avoiding an unconditional source
of the whole case-divergence library just for one comparison).

Both functions do the same thing: `shopt -s nocasematch` then `[[ "$1" == "$2" ]]`. bash's
`nocasematch` pattern matching follows the active `LC_CTYPE` locale's case-folding rules, not a
fixed ASCII table -- under an unusual locale (Turkish `tr_TR.UTF-8` is the textbook example, where
ASCII `I`/`i` fold differently than in the `C`/`en_US` locales) the fold could, in principle,
disagree with the filesystem's own case-insensitive semantics, which are locale-independent.

Other locale-sensitive spots in this same codebase (`_resolve_remember_dir`, `_set_store_root`)
explicitly pin `local LC_ALL=C` before doing byte-wise/bracket-range work for exactly this reason.
Neither `_remember_case_fold_eq` (pre-existing, #298) nor `_remember_th_ci_eq` (new, #721) does.

Reviewer-ranked severity: low -- narrow, platform/locale-dependent, and `_remember_th_ci_eq`
matches an existing, already-accepted convention in this same file rather than introducing a new
one. Worth a curation pass deciding whether both functions should gain `local LC_ALL=C` in one
sweep, since fixing only the new one would leave the older #298 helper as the one example that
still doesn't follow the file's own stated convention.
