#966: the TOCTOU-window fix in `hooks.d/after_save/60-git-reconcile.sh`'s
`_grc_report_conflict` only narrows the race, it does not close it fully. Two
residual windows, both found by a self-review spawn (Explore) and independently
confirmed by the `oss:auditor` spawn's own "fails-to-preserve" note, on the
same lane that opened #966.

1. The content snapshot is taken immediately before `git rebase --quit`, not
   before the rebase attempt itself (`git rebase --no-autostash "$REMOTE_REF"`,
   several hundred lines above where `_GRC_TOUCHED_PATHS` is first computed).
   A concurrent write from a different slug landing on a shared touched path
   any time between the rebase starting and the snapshot being taken is
   already reflected in the "before" snapshot, so the post-quit comparison
   cannot see it and the path is restored/removed anyway -- discarding that
   write while the hook still logs "aborted, the tree is unchanged" (or
   "restored"). Deliberately not moved earlier: snapshotting before the
   rebase attempt itself would also capture every touched path's legitimate
   pre-rebase content, which always differs from whatever this run's OWN
   replay left there once it conflicts -- so EVERY touched path would look
   "changed" and the restore would never restore anything, which is a worse
   regression than the one #966 reports. Closing this needs a mechanism that
   can tell this run's own rebase replay apart from a different slug's write,
   not merely "before this run" vs "after" -- out of scope for #966's fix.

2. A second, much narrower gap sits inside the fix's own intended window: all
   per-path "now" hashes are computed in one loop (building `_grc_safe_paths`)
   before the actual `git checkout HEAD --` / `git rm -f` calls run on that
   whole set. A write landing after a given path's hash was read, but before
   that path's own checkout/rm executes, is undetected and still clobbered.
   The window is small (a handful of subprocess calls) but grows with the
   size of the touched-path set, since every path's hash is computed before
   any path is acted on.

Neither gap is exercised by the new regression test added in #966's own fix
(which only exercises a write landing during the `rebase --quit` subprocess
call itself, matching the sibling pre-existing TOCTOU test's own shape) --
both would need a new test fixture with a different injection point to catch.

Not decided here: whether either gap is worth a dedicated follow-up issue, a
jit-context rule, or neither. Logged for /oss:curate to weigh, holding
whatever else is in trap.d/ at the same time.
