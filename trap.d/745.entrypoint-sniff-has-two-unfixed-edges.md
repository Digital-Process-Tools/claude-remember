#745, carried over from an earlier lane's self-review round on the same fix (two spawned
reviewers, Explore + oss:auditor, converged independently on the same root cause).

`_transcript_is_pluginless_sdk()` (scripts/session-start-hook.sh) excludes a candidate transcript
from ever being "the previous session" purely on its own `entrypoint` field opening with `sdk-`.
Two edges left open, ranked by the auditor as `misreports` / non-blocking / "can ship behind a
trap.d fragment" rather than a release blocker:

1. **No evidence check.** The exclusion has no way to tell a pluginless SDK session (the reported
   bug -- `setting_sources=[]`, no plugins loaded, no marker ever possible) apart from a
   hypothetical SDK integration that DOES pass `setting_sources` and loads this plugin, which would
   write its own `capture-alive.d/<id>` marker exactly like any other host. The current code
   excludes both, unconditionally, by prefix alone. A marker- or save-record-aware refinement
   (check `capture_was_seen`/`session_was_saved` on the candidate's OWN filename id before
   excluding it) would close this, but `CAPTURE_SEEN_DIR` is assigned later in
   `_remember_deferred_phase` than `previous_transcript()` is called, so wiring it in safely means
   either moving that assignment earlier or threading the check through `session_was_saved` alone
   (which does not depend on `CAPTURE_SEEN_DIR`) -- needs a deliberate ordering audit, not a
   five-minute patch. No real-world instance of a plugin-loaded SDK entrypoint has been observed;
   #745's own dataset (kenspc's 16 transcripts) had none, all 25 SDK-entrypoint ones were
   pluginless.

2. **Substring scan, not a JSON parse (mitigated, not eliminated).** The sniff is `case "$line" in
   *'"entrypoint"'*)`, a raw substring match over up to 50 lines, not a real per-key parse. A line
   carrying a `"message"` field is skipped outright before the entrypoint check even runs, which
   closes the concrete, almost self-referential scenario self-review raised (a transcript of a
   session discussing THIS issue's own test fixtures, which literally contain the string
   `"entrypoint":"sdk-py"`, would otherwise have matched on ordinary dialogue). A residual false
   match confined to a bookkeeping-shaped, non-dialogue line that happens to embed the substring in
   some nested value (an attachment's own file content, say) is not eliminated by this mitigation.

3. **The message-field skip can mask the exact bug it was added to prevent (auditor finding, this
   follow-up lane).** `_transcript_is_pluginless_sdk()` skips any line carrying a `"message"` key
   before checking `entrypoint`, closing the false-positive direction (ordinary dialogue quoting
   the literal string `entrypoint`/`sdk-py`). Not checked in either direction: whether an Agent
   SDK bookkeeping record itself can ever carry a top-level `"message"` key that is not the
   dialogue-content field (an error or status string on the same `queue-operation` record, say).
   If it can, and that is the only line inside the 50-line cap carrying `entrypoint`, the guard
   silently never fires and the exact false notice / force-save #745 fixes reappears for that
   transcript. No test exercises this shape in either direction, and the two datasets gathered for
   this issue (kenspc's 16 transcripts, this follow-up lane's own review) are evidence only that
   this specific variant was not observed there, not that Claude Code's SDK bookkeeping schema
   cannot produce it -- unverified against upstream's own schema.

Whether any of these is worth a real fix, and what the fix should look like, is a curation
decision, not one to make mid-lane holding only this one issue's context.
