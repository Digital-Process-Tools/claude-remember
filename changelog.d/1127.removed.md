- Removed: automatic takeover of a save/consolidation/staging lock whose
  pid file cannot be read (#1127) -- the dataless cloud-sync placeholder case
  (OneDrive, iCloud: the remote copy of a synced file was deleted after
  the placeholder itself synced). Since v0.45.1 (#1101, #1103), a lock
  left in that state was eventually taken over automatically once it had
  sat untouched long enough. Five review rounds in a row (#1119, #1122,
  #1124/#1125, the reviews on pull request #1126) each found a new way
  for two processes to end up believing they both held the same lock
  through that takeover, however it was tightened in response to the
  previous finding. Rather than continue patching an unsafe design, this
  takeover is switched off: a pid file that cannot be read, at any age,
  is refused rather than stolen or adopted, the same as before v0.45.1.
  If this happens to you (a save, consolidation or staging step appears
  stuck, logging "another process holds the lock, skipping" repeatedly),
  the lock directory now has to be cleared by hand: delete the stale
  `.lock` directory shown in that message (`save.lock`,
  `consolidation.lock` or `staging.lock`, inside your `.remember/`
  store) once you have confirmed no genuine save is still running.
  Everything else from v0.45.1 is unchanged: the bounded (2-second) pid
  read, reclaiming a dead holder's pid file that reads fine (whether
  empty or garbage), the Ubuntu 26.04 `noclobber` guard, and the
  age-gated takeover of a holder that is still alive but has held the
  lock past `REMEMBER_LOCK_MAX_HOLD_SECONDS` -- that last one still
  requires a pid file that reads successfully, and is kept because both
  sides of it (the steal and the ordinary release) resolve their race
  through the same atomic-rename mechanism already proven for the
  confirmed-dead-holder case, with no read-failure ambiguity involved.
- Compatibility: compatible - a lock that used to recover on its own
  after a long wait now instead needs a manual delete of the lock
  directory; no command, config key or file format changes, and no
  caller of `lock_acquire`/`lock_release` changes its own interface.
