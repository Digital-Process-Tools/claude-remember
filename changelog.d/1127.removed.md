- Removed: automatic takeover of a save/consolidation/staging lock whose
  pid file cannot be read (#1127) -- the dataless cloud-sync placeholder case
  (OneDrive, iCloud: the remote copy of a synced file was deleted after
  the placeholder itself synced). Since v0.45.1 (#1101, #1103), a lock
  left in that state was eventually taken over automatically once it had
  sat untouched long enough. Five review rounds in a row (#1119, #1122,
  #1124, #1125, and the reviews on pull request #1126) each found a new
  way for two processes to end up believing they both held the same
  lock through that takeover, however it was tightened in response to
  the previous finding. Rather than continue patching an unsafe design,
  this takeover is switched off: a pid file that cannot be read, at any
  age, is refused rather than stolen or adopted, the same as before
  v0.45.1. A further review round on this fix's own pull request
  (#1129) found two more races in the behaviour this change keeps --
  closed in the same commit: an EMPTY pid file (not merely unreadable)
  is now also never grounds to steal, at any age, because every
  legitimate winner's own pid write passes through a briefly-empty
  state that an unrelated dead holder's permanently-empty pid file is
  indistinguishable from; and releasing a lock now refuses whenever its
  own read of the pid file comes back empty, rather than treating an
  empty read as "ownership unproven, but proceed anyway."
  If this happens to you: a save, a consolidation round, or an append
  to today's running notes quietly stops completing -- nothing crashes
  and nothing shows an error unless debug logging is on, it just
  stops happening, so the way most people notice is that nothing new
  is being remembered for a while. If you suspect this, first make
  sure no Claude session that uses this plugin is currently open or
  running -- only then is it safe to clear the lock. Memory lives in a
  folder named `.remember` -- either inside your project (the
  default), or in your home folder as `.remember/<project-name>`
  if you're using "external storage mode" (see
  docs/external-storage-mode.md). Inside that `.remember` folder is a
  `tmp` folder, and inside `tmp` are the three lock folders this can
  affect: `save.lock`, `consolidation.lock` and `staging.lock`. With
  no Claude session open, delete whichever of those three folders
  exists (not the files inside your `.remember` folder, just that one
  small lock folder) and the next save or consolidation will work
  normally again.
  Everything else from v0.45.1 is unchanged: the bounded (2-second) pid
  read, reclaiming a dead holder's pid file that reads back as garbage
  (non-numeric, but not empty), the Ubuntu 26.04 `noclobber` guard, and
  the age-gated takeover of a holder that is still alive but has held
  the lock past `REMEMBER_LOCK_MAX_HOLD_SECONDS`. That last one still
  requires a pid file that reads back successfully and non-empty, and
  is kept because both sides of it (the steal and the ordinary
  release) resolve their race through the same atomic-rename mechanism
  already proven for the confirmed-dead-holder case, now with the
  empty-read ambiguity above closed on both sides too.
- Compatibility: compatible - a lock that used to recover on its own
  after a long wait now instead needs a manual delete of the lock
  folder; no command, config key or file format changes, and no
  caller of `lock_acquire`/`lock_release` changes its own interface.
