- Fixed #1047: `session-start-hook.sh`'s field extractor (`_stdin_json_string_into`) used `${var#*pattern}`, which is quadratic in bash -- O(n^2) on the raw payload's length. A host that pipes a whole transcript in as SessionStart's stdin (legal; the hook cannot refuse it) handed this function a multi-megabyte string: the reporter observed 27 `session-start-hook.sh` processes alive 21 hours each, immune to `SIGTERM` (a single builtin runs for hours with no signal check). Fixed by bounding the raw argument to the match itself (4096 bytes) rather than truncating `HOOK_STDIN`'s own accumulation, which the `before_session_start`/`after_session_start` listener-publish block (#266) still needs byte-identical up to its own 32 KiB cap. The four fields this hook ever extracts (`cwd`, `session_id`, `transcript_path`, `source`) sit in the first few hundred bytes of every legitimate payload, so the bound is a no-op for real-world traffic and only ever discards an adversarial tail. Out of scope: the three sibling hooks sharing the same operator (`post-tool-hook.sh`, `session-end-hook.sh`, `user-prompt-hook.sh`) and `capture-gap-check.sh`'s own copy (used against transcript file lines, not host stdin) -- noted in the issue's own comment thread as needing their own measurement, since a `PostToolUse` payload can legitimately carry a large tool result and a blanket 4 KB scan window there is a real behaviour question, not a drive-by.
