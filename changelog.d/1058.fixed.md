- Fixed #1058: `write-handoff.sh` could misroute a handoff when the Bash cwd had moved deeper than the subdirectory project a session actually started in. The #776 fix compared only two candidates ($(pwd) and the git toplevel) for the session-keyed hint; a directory strictly between the two -- reached only by a `cd` further down -- was invisible to it, and the write fell through to the enclosing repository's own store. Replaced the two-candidate check with a walk of every ancestor from $(pwd) up to the git toplevel, picking whichever ancestor's own store carries the FRESHEST copy of the session's hint (not simply the nearest one, so a `--resume` that republishes the hint at a different ancestor than an earlier, now-stale one is still routed correctly) and terminating safely even on a Windows/MSYS UNC path. `scripts/doctor.sh`'s own project-dir resolver got the identical fix, so `/remember:doctor` reports the same store write-handoff.sh actually writes into.

  **Known limits, left open for #1083**: this walk only ever considers directories on the path from $(pwd) up to the git toplevel. It does not, and structurally cannot, help when a session resumes into a directory that is NOT an ancestor of the later cwd (a sibling or child of the original start dir) -- that case, plus a nested repository/submodule (the walk stops at the innermost toplevel) and a non-git sibling directory (no walk runs at all when $(pwd) is outside any git repo), are pre-existing #743/#776 architecture, not a regression introduced by this fix. #1083 tracks pinning the resolved store at SessionStart instead of guessing from cwd, which would close those three together. A fourth limit, not yet filed: two ancestors' hints written in the same second (mtime granularity -- as coarse as 2 seconds on some filesystems) tie-break on whichever the walk happens to visit last, not on which one is actually newer.
