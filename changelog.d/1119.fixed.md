- Fixed: `_lock_read_pid_timeout` (`scripts/lib-lock.sh`) treated a FAST,
  ordinary read failure (permission denied, I/O error, a cloud-sync
  placeholder that errors rather than hangs) exactly like a successful read
  of a genuinely empty pid file, a regression from the #1101/#1103 lock-
  staleness fix (v0.45.1). Because a confirmed-empty pid file is reclaimed
  after only `REMEMBER_LOCK_ADOPT_AFTER` (30s) rather than
  `REMEMBER_LOCK_MAX_HOLD_SECONDS` (1800s), this let a second process steal
  `save.lock`/`consolidation.lock`/`staging.lock` away from a holder that
  was still alive, 60x sooner than any other takeover path allows (#1119).
  A fast read failure is now treated the same as a read that never
  completed: refused on its own, but still recoverable through the
  existing age-gated takeover once the lock directory is older than
  `REMEMBER_LOCK_MAX_HOLD_SECONDS`.
- Corrects the v0.45.1 changelog entry for #1101/#1103, which claimed a
  confirmed-empty pid file is "reclaimed too, exactly as it already was for
  the no-pid-file-at-all case" -- not true for a pid file that reads empty
  because the read failed fast rather than because it genuinely is empty;
  v0.45.0 never stole a lock in that case either (#1119).
