- Fixed: `log()` (`scripts/log.sh`) forked a `printf | tr` pipeline on every
  single call to flatten control bytes (#599), even though the large
  majority of log messages this codebase actually writes carry no control
  byte at all. `log()` runs on the per-tool-call hot path
  (`post-tool-hook.sh` logs at least once per invocation). A cheap in-shell
  pattern match now decides whether a message needs flattening before
  paying for the fork -- the fork itself, and its correctness (`LC_ALL=C`,
  same reasoning as #599), are unchanged for a message that actually
  contains one (#621).

  The pre-check tests literal byte values (an ANSI-C quoted range) rather
  than the POSIX `[[:cntrl:]]` bracket class it originally used, which is
  never wrong to prefer (no ctype/locale table lookup, nothing for a
  different bash build to classify differently) -- but whether the
  `[[:cntrl:]]` version genuinely ever failed on windows-latest CI is, on
  the evidence gathered across two CI round-trips, no longer established.
  The first windows-latest failure (one test, the embedded-newline case)
  and the second (five tests, every control-byte class the test file
  covers, all with the identical symptom: the message came out correctly
  flattened, but the test's own detection of "did `tr` run" never fired)
  both trace to the SAME root cause, found on the second round-trip: the
  test harness's own `tr`-interception stub was never actually reached on
  that platform, because it prepended the stub's directory onto `$PATH`
  through Python's `subprocess` `env=` dict using `os.pathsep` (`;` on
  Windows) -- but Git Bash's `bash.exe` is a POSIX shell and always wants
  `$PATH` colon-separated internally, regardless of host OS, so the
  semicolon-joined value could not be parsed the way the test intended, and
  the REAL system `tr` ran in the stub's place, silently, correctly
  flattening the message either way. Fixed by prepending the stub's
  directory to `$PATH` from INSIDE the bash script itself (`export
  PATH="$BINDIR:$PATH"`, a literal colon, extending bash's own
  already-POSIX `$PATH`) rather than through the Python-constructed env
  dict -- eliminating the ambiguity rather than the byte-range change
  above, which was reasoned defense-in-depth for a hypothesis this evidence
  can no longer confirm or rule out either way.
