## Reading the transcript path the host hands us

`SessionStart` and `SessionEnd` carry `transcript_path` on their stdin payload, and since [#407](https://github.com/Digital-Process-Tools/claude-remember/issues/407) the pipeline reads it instead of reconstructing it. `pipeline/extract.py`'s `find_session()` uses the supplied path verbatim when it names a real file — no slug, no glob, none of the drive-letter and truncation logic above enters into it. Every failure mode that logic guards against (six Windows drive spellings, a 200-character truncation boundary, an astral character counted differently by two implementations) exists only because a *derived* path can disagree with where the host actually wrote; a path the host handed over cannot.

The two hooks that already read this stdin payload for `session_id` (`scripts/session-start-hook.sh`, `scripts/session-end-hook.sh`) extract `transcript_path` from the same payload with the same narrow, validated-after-extraction heuristic, and export it as `REMEMBER_TRANSCRIPT_PATH` for any Python process they spawn. `pipeline/host.transcript_path()` reads that variable and returns `None` — never a guess — for anything it cannot open: unset, blank, a directory, a path that does not exist. `_session_dir()`'s reconstruction stays exactly where it was, as the fallback for any caller with no payload to read at all.

**This is an existence check only, not a containment check** ([#424](https://github.com/Digital-Process-Tools/claude-remember/issues/424)): `pipeline/extract.py`'s `find_session()` returns whatever `transcript_path()` hands it before its own traversal validation ever runs, so a `REMEMBER_TRANSCRIPT_PATH` set anywhere in the ambient environment -- not written by either hook -- is trusted unconditionally. **[#431](https://github.com/Digital-Process-Tools/claude-remember/issues/431) is the decision, not an open gap**, and it splits callers into two groups:

- **Hardened.** `scripts/post-tool-hook.sh` and `scripts/user-prompt-hook.sh` trigger routine autosaves on every tool call, with no human watching and no `transcript_path` of their own to offer — they `unset REMEMBER_TRANSCRIPT_PATH` before doing anything else, so an ambient value (a `.envrc`, a leftover from a different session) can never reach them.
- **Trusted by design.** A manual `scripts/save-session.sh` run, `scripts/doctor.sh`, and a direct `pipeline.extract` invocation from the command line have no hook preamble to clear anything in, and inherit the ambient environment on purpose — the same way they already inherit `$PATH` or `$HOME`. No containment check was added, because `pipeline/host.transcript_path()` and `pipeline/extract.py`'s `find_session()` are the ONE channel both a legitimately-supplied value and an ambient one travel through: `scripts/session-start-hook.sh`/`scripts/session-end-hook.sh` export the legitimate one fresh, from their own validated stdin payload, on every run, and trusting wherever the host says the transcript lives — rather than reconstructing it — is the whole point of [#407](https://github.com/Digital-Process-Tools/claude-remember/issues/407). A containment rule narrow enough to matter would also reject that legitimate value on a host or a mount this repo does not model: `CLAUDE_CONFIG_DIR`/`~/.claude` is itself a relocatable, user-set path (not "never" the project directory either — see [#166](https://github.com/Digital-Process-Tools/claude-remember/issues/166)), and it is Claude Code's own layout, not a Codex- or Gemini-neutral one — exactly the host-specific seam `pipeline/host.py`'s own module docstring declines to invent. `scripts/doctor.sh` says the decision out loud instead: it prints a `WARN` naming the value when it finds one in its own environment, rather than silently trusting it. See `pipeline/host.transcript_path()`'s docstring for the fuller argument.

**The session id an incremental save resumes from now also prefers the supplied one over the transcript's basename.** A host is free to name its transcript file anything — Codex writes `rollout-<date>-<uuid>.jsonl` — and a basename-derived id that never matches what was actually passed in would key `get_last_save_line` on the wrong string, silently re-summarizing the whole transcript on every save (the duplicate [#140](https://github.com/Digital-Process-Tools/claude-remember/issues/140) exists to prevent).

**`pipeline/host.py` also reads the plugin's own install directory** through `PLUGIN_ROOT_VARS`, in the same host-neutral spirit: the vendor-neutral `PLUGIN_ROOT` (read by `scripts/resolve-paths.sh` before its `CLAUDE_PLUGIN_ROOT` fallback) wins over `CLAUDE_PLUGIN_ROOT`, which Codex also sets but only as a compatibility alias it could withdraw in any release. `tests/test_host_shell_parity_407.py::test_host_shell_parity` keeps the shell script's hand-mirrored variable list from drifting out of sync with `pipeline/host.PLUGIN_ROOT_VARS`, the same way `tests/test_slug_parity.py` already guards `scripts/lib-slug.sh` against `pipeline/slug.py`. **Neither name is trusted on `[ -d ]` alone** ([#471](https://github.com/Digital-Process-Tools/claude-remember/issues/471)): `resolve-paths.sh` requires `pipeline/haiku.py` under whichever directory wins, so an unrelated tool that happens to export the same generic `PLUGIN_ROOT` name into a hook's environment falls through to `CLAUDE_PLUGIN_ROOT` instead of becoming this plugin's execution root.

This is deliberately a thin data table, not a host abstraction layer — `pipeline/host.py`'s own module docstring says what was left out and why (event names live in each host's manifest; the summarizer, `pipeline/haiku.py`, is Claude-Code-coupled by design and not touched). A host nobody has described yet (`detect_host()`'s `UNKNOWN`) is a normal result: everything this plugin actually needs from a host arrives on stdin regardless of whether the plugin recognises it.

**The project root itself has the same fallback, since [#411](https://github.com/Digital-Process-Tools/claude-remember/issues/411).** `scripts/resolve-paths.sh` used to resolve `PROJECT_DIR` from `CLAUDE_PROJECT_DIR` alone, which Codex never sets (live-confirmed, #463) and which Gemini CLI was then believed never to set either -- on either host resolution failed outright and every hook took its `|| exit 0`, silently inert. That belief about Gemini turned out to be wrong: its own bundled docs list `CLAUDE_PROJECT_DIR` as a compatibility alias it does set (#456, unverified live -- #532), so the fallback below is not what makes Gemini resolvable any more, though it stays correct and needed for Codex and any host that genuinely leaves the variable unset (#534). `session-start-hook.sh` and `session-end-hook.sh` now read stdin's `cwd` field (present on all three hosts' `SessionStart`/`SessionEnd` payload) before sourcing `resolve-paths.sh`, and export it as `REMEMBER_HOOK_CWD` for the resolver to consult. Precedence is `CLAUDE_PROJECT_DIR`, then `REMEMBER_HOOK_CWD`, then the existing local-install derivation, then the existing loud failure — a stdin `cwd` disagreeing with a *set* `CLAUDE_PROJECT_DIR` never wins, because the environment variable is the more specific signal on the host that publishes it. Reading stdin earlier than before meant duplicating the `REMEMBER_NESTED_SUMMARIZER` fast-path guard ahead of the capture in `session-start-hook.sh`, matching the copy the other three hooks already carry for the same reason — without it, the nested summarizer's stdin read would cost up to a second per session it never needed to pay (measured: ~1.03s unguarded vs. ~5-13ms with the guard, both with stdin held open).
