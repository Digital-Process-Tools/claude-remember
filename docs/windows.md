# Windows

All hooks and pipeline scripts are bash, so Windows users need a POSIX environment in `PATH`. This page carries the full Windows record: what the CI badge does and does not prove, the supported shells, and the platform-specific defects found so far. Moved verbatim from the README. See also [windows-skip-triage.md](windows-skip-triage.md) for the skip audit.

**The "Windows" in the README's OS badge is honest about the platform, not about the coverage** ([#497](https://github.com/Digital-Process-Tools/claude-remember/issues/497)): most of the suite still blanket-skips on `win32` rather than actually running there, and the `windows-latest` legs report `success` either way. [Running tests](running-tests.md) says exactly how much, and every `pytest` run — including the CI leg itself — now prints the live skip ratio rather than leaving it silent.

## Supported environments

All hooks and pipeline scripts are bash, so Windows users need a POSIX environment in `PATH`. Two supported options:

- **Git Bash / MSYS2** (simplest) — installed by [Git for Windows](https://git-scm.com/download/win). Ships bash, coreutils, and `find`/`tar`/`tr`. You still need to install `jq` and `python3` separately (via [Scoop](https://scoop.sh/), [Chocolatey](https://chocolatey.org/), or the [official installers](https://www.python.org/downloads/windows/)).
- **WSL** — any Linux distro; works like a native Linux install.

Make sure `bash`, `jq`, and `python3` are resolvable from the shell your coding agent launches hooks in.

**bash's own glob and parameter-expansion pattern matching (`*`, `%/*`, `##*/`, a `[[ == ]]` glob) recognise only `/` as a path separator, never a backslash** — and on Git Bash/MSYS2, `resolve-paths.sh` hands the plugin's own directory variables (`REMEMBER_DIR`, `PROJECT_DIR`) to the rest of the scripts fully backslash-separated, the native Windows form. [#487](https://github.com/Digital-Process-Tools/claude-remember/issues/487) and [#517](https://github.com/Digital-Process-Tools/claude-remember/issues/517) fixed the 8 places this silently broke on that platform (7 named in #517, one of which -- the case-divergence check -- needed two call sites fixed together, plus #487's own retention sweep) across `run-consolidation.sh`, `session-start-hook.sh` (staging/rotation counts feeding the session banner, and the #373 stale-delivery-record pruner), `lib-case-divergence.sh`, and `doctor.sh` (storage-mode detection and two byte/count diagnostics), via one shared helper, `_remember_forward_slash` (`scripts/resolve-paths.sh`), that every later call site normalizing one of these variables before a glob or pattern match now reuses rather than re-deriving the `$OSTYPE` gate itself. (An absolute running total of `_remember_forward_slash` call sites used to be stated here; it drifted stale twice -- see #524 -- so this doc now lets the per-issue breakdown below stand on its own rather than restating a count nothing recomputes.) [#519](https://github.com/Digital-Process-Tools/claude-remember/issues/519) fixed the 2 further sites in the same family that #517's own self-review found but did not fix, being outside that lane's own claimed files: `scripts/bootstrap-dirs.sh`'s in-project `.gitignore` write and `hooks.d/before_session_start/50-git-restore.sh`'s legacy-mode guard, both the identical `$OSTYPE` gate duplicated inline rather than calling the shared `_remember_forward_slash` function -- neither site can rely on it being in scope. The git-restore.sh hook is exec'd as its own process by `dispatch()`, never sourced, so a function `resolve-paths.sh` defines in the parent process is not in scope there, and the file deliberately never sources `resolve-paths.sh` itself to keep its own "cheap guards first" cost promise for the legacy-mode majority that can never activate the hook at all. bootstrap-dirs.sh's own USAGE header claims every caller sources `resolve-paths.sh` first, but a real caller -- `tests/test_external_data_dir.py` and `tests/test_worktree_memory.py`'s own end-to-end harnesses -- sources only `detect-tools.sh` and `bootstrap-dirs.sh`, never `resolve-paths.sh`; calling the shared helper there is silently `command not found`, degrading the whole gate to "never matches, `.gitignore` never written" for every `REMEMBER_DIR`, not just a backslash-laden one -- caught by CI (ubuntu-latest 3.9, job 100934963344) after an initial commit that did call it directly. The `git-restore.sh` site was live, not merely theoretical: under the bug, a backslash-separated `REMEMBER_DIR` on an affected Windows install with `git_restore.enabled=true` made the later `git -C "$REPO_ROOT" rev-parse --show-toplevel` toplevel check disagree with the (wrongly unsplit) `$REPO_ROOT`, so the hook's own "declined: not the toplevel of its git repository" refusal fired unconditionally and the restore silently never ran, for every `REMEMBER_DIR`, legacy or external. [#524](https://github.com/Digital-Process-Tools/claude-remember/issues/524), [#525](https://github.com/Digital-Process-Tools/claude-remember/issues/525) and [#526](https://github.com/Digital-Process-Tools/claude-remember/issues/526) fixed 3 more sites the gate-3 release audit ahead of v0.26.0 found in the same two files -- `doctor.sh`'s `_SESSION_END_FIRED` glob (misreporting SessionEnd as never having fired) and its memory-file count (the third undercounting-to-0 counter in the file, after the two #517 already named), plus `run-consolidation.sh`'s `.tail-*`/`.prefix-*` stray-sibling cleanup (one inert temp file per failed split, left un-normalized when #517 fixed the snapshot sweep 134 lines above it in the same file).

**If `UserPromptSubmit` still feels slow on a warmed project** ([#511](https://github.com/Digital-Process-Tools/claude-remember/issues/511)): each `bash` command substitution — `$( ... )` — forks a subshell, which is cheap on Linux/macOS and measurably slower on Windows Git Bash, independent of whether anything inside it shells out to an external process at all. `user-prompt-hook.sh`'s warm path forks fewer of these than it used to (the `cwd` extraction and the clock read now write into a variable directly instead of being captured through one), but one remains structurally: the block that builds the line it prints has to be captured whole so it can be folded into one JSON reply on hosts/notices that need that shape. Setting `prompt_stamp: "stable"` in `config.json` (see [Configuration](configuration.md)) removes the clock read entirely and prints only `[username]`, which is the cheapest and most stable option if the per-prompt line is not something you read closely. This is **reasoned, not measured** — nobody on this project has a Windows box to time it on.

**A jq-less install (`jq` not on `PATH`, the default for a fresh Git for Windows install per the "Supported environments" note above) used to spawn `save-session.sh --force` in the background on *every* SessionStart, even for a session that genuinely had been saved** ([#667](https://github.com/Digital-Process-Tools/claude-remember/issues/667)): `session_was_saved()`'s jq-less shim dropped its own `--arg` flag and the session-id value along with it, so the query it actually ran was on the wrong two arguments and it always answered "unsaved". Fixed by giving `session_was_saved()` a dedicated jq-free branch. `jq` is still the recommended, better-tested path on Windows (see Requirements) — this fix only corrects one specific jq-less code path, not a claim that `jq` is now unnecessary everywhere in this codebase.

**A host that does not set `CLAUDE_PROJECT_DIR` -- Codex never does -- hands the hooks the project directory as the payload's JSON `cwd`, where a Windows path is written `C:\\work\\proj`** ([#829](https://github.com/Digital-Process-Tools/claude-remember/issues/829)). The hooks' stdin extractors decode each `\\` back to one backslash before anything derives a path or a Claude Code session-directory slug from the value. Left doubled, the slug came out `c---work--proj` rather than `c--work-proj`, and a Codex-hosted SessionStart could not find the previous Claude Code session it tries to recover.

**With Windows Terminal as the default terminal, PostToolUse's detached save briefly flashed its own console window every few minutes** ([#1002](https://github.com/Digital-Process-Tools/claude-remember/issues/1002), reported by fmatamala): a plain nohup-and-background launch still allocates a console on Windows regardless of how the parent script was itself invoked. That one site now routes through a hidden `wscript.exe` launcher first (`scripts/lib-detach.sh`), falling back to the unchanged nohup line -- never to silently skipping the save -- whenever the hidden route is unavailable. **This is REASONED, not OBSERVED**: nobody on this project has a Windows box to confirm no console actually flashes with the new route.

**Round 2 (v0.42.3 release-audit, gate 3): two REASONED-only gaps in that first fix, settled with real `wscript.exe` evidence.** The release audit raised two claims no CI leg could see at the time, because the hidden-route tests stub `wscript.exe` with a bash shim rather than exercising Windows Script Host for real: (A) the launcher built a `bash -c SCRIPT` whose script string embedded literal double quotes in one argv entry, and whether that quote survived the exec->CreateProcess->WSH argv hop unmangled was never confirmed on a real Windows host; (B) if WSH itself is disabled by policy, the launcher backgrounded `wscript.exe` and unconditionally returned success, so the caller's own nohup fallback never fired -- a silent skip. `tests/test_windows_real_wscript_1002.py` now drives the real launcher, the real VBS and the real `wscript.exe` on the `windows-latest` CI legs (never stubbed there), with a plain path, a path containing a space, and WSH disabled via the registry. The fix removes the embedded-quote argv entry entirely (`scripts/lib-detach-pidwrap.sh` now takes OUTFILE as its own argv entry and does its own redirect, so no argument on the call ever carries a literal quote) and runs `wscript.exe` in the foreground so its own exit status -- non-zero when WSH itself could not run anything -- now reaches the caller and triggers the nohup fallback instead of a silent skip.

The plugin's other three detached launches -- SessionStart's consolidation, SessionEnd's self-redetach, and the Antigravity Stop hook's save -- are intentionally NOT wired to the hidden launcher yet, and are tracked in [#1006](https://github.com/Digital-Process-Tools/claude-remember/issues/1006): SessionStart's own compiled release-tree size has no budget margin left to absorb it, and wiring SessionEnd's self-redetach surfaced a real regression under review -- a wscript-launched child does not inherit the parent process's stdin the way `nohup ... &` does, so SessionEnd would lose the hook's own JSON payload (no cwd, no session id) on the hidden route. Those three sites keep their unchanged nohup lines for now, so they still flash a console on Windows, the same as before this fix.

**Round 3 (#1002, maintainer instruction): the fixed v0.42.3 shape, a stall regression in that fix, and real wscript.exe evidence against the shape v0.42.3 actually shipped.** Round 2 fixed the code based on two REASONED-only claims and then observed the NEW shape working on real Windows Script Host, but never ran the OLD, actually-shipped v0.42.3 shape against real WSH -- so whether v0.42.3 itself was broken in production was never settled by observation alone. `tests/test_windows_real_wscript_v0_42_3_1002.py` closes that gap: it drives the exact bytes `v0.42.3` shipped (vendored under `tests/fixtures/v0_42_3/`, never edited to track later fixes) against a real `wscript.exe`, on the same three cases round 2 already proved the NEW shape handles.

**v0.42.3 OBSERVED, on PR #1010's own `windows-latest` CI legs (run #38049234152, jobs 114204833302/114204833300/114204833325/114204833251/114204833202): all three cases failed, every leg, confirming both trap fragments for the first time rather than reasoning about them.** Plain path and path-with-a-space both returned `RC=0` from the shipped `_remember_detach_windows` but the save script never actually ran (trap A -- WSH's own argv parser corrupts the embedded literal quote in v0.42.3's own `c_script`); the path-with-a-space case additionally corrupted the OUTFILE argument itself into a garbled relative filename that landed in the CI job's own working directory rather than under the test's own tmp path. WSH-disabled confirmed trap B directly: the save never happened within the poll window, because the shipped shape backgrounds `wscript.exe` and unconditionally returns 0, so the caller's nohup fallback never fires. All three are pinned `xfail(strict=True)` in that module with the job ids and exact failure above as the reason, so the suite stays green while the evidence stays observed rather than erased.

The round-2 foreground `wscript.exe` call is bounded by a plain bash background-job-plus-watchdog pair (`sleep`, then `kill -9` on timeout) rather than the external `timeout` binary, because that coreutils tool is not guaranteed present on every host this suite's own stub-based tests simulate Windows on (observed absent on a bare macos-latest CI image). With Windows Script Host disabled by policy, every `_remember_detach_windows` call used to pay that full watchdog bound before falling back to `nohup` -- and PostToolUse calls this function on every tool call, so an affected host stalled every single save by that amount, forever, not just once. `scripts/lib-detach.sh` now caches the "hidden route unusable" verdict (keyed on the whole `$PATH` string, the same identity `scripts/detect-tools.sh`'s own #668 tool-verdict cache uses) after the first failure, so every later call on that host goes straight to the `nohup` fallback, paying neither the checks nor the watchdog bound again. Only the unusable verdict is cached -- a usable one is cheap to re-earn and caching it would let a host that becomes unusable mid-session (WSH disabled while a session is open) keep being told it is fine.

`tests/test_windows_real_wscript_1002.py::test_real_wscript_healthy_path_latency` measures the real hook-entry-to-return cost of the hidden route against the plain `nohup` route on real `windows-latest` CI legs, over several runs, printed in the job log -- the basis for sizing the watchdog bound against an actual number rather than a guess (#913, PostToolUse latency, is the open issue this feeds).
